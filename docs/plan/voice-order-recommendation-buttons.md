# 음성 주문·메뉴 추천 버튼 분리 구현 계획

- 작성일: 2026-11-10
- 상태: 4.1~4.4 구현 완료. 4.5 통합 문서·검증 정리는 후속 작업
- 관련 기능: [음성 옵션 자동 선택](voice-order-option-autoselect.md), [API 계약](../api-spec.md)

## 1. 목표와 화면 범위

음성 입력 전에 사용자가 주문 또는 추천 목적을 직접 선택한다. 음성 주문 화면의 하단 `음성 녹음` 버튼을 왼쪽 `주문하기`, 오른쪽 `메뉴 추천받기` 버튼으로 나누고, 두 버튼 모두 기존 `MicrophoneIcon`을 사용한다. `음성 또는 터치로 주문해 주세요.` 하단 안내는 제거한다.

이 계획은 시작 화면의 `음성으로 주문하기` 진입 버튼을 유지하고, 진입 후 음성 주문 화면의 하단 조작 영역을 변경하는 것으로 잡는다. 메뉴 선택 전인 초기 화면과 추천 목록에서 두 버튼을 표시한다. 메뉴 확인·온도·커스터마이징·매장/포장·최종 확인 단계에서는 해당 단계에 답하는 기존 단일 녹음 조작을 유지한다. 주문 진행 중 새 추천으로 전환하여 선택한 주문을 버리는 기능은 이번 범위에 포함하지 않는다.

대기 상태의 화면 배치:

```text
┌─────────────────────┬─────────────────────┐
│  [마이크] 주문하기   │ [마이크] 메뉴 추천받기 │
└─────────────────────┴─────────────────────┘
```

두 버튼은 같은 너비로 배치한다. 좁은 화면에서도 왼쪽/오른쪽 순서를 유지하며 버튼 텍스트는 필요하면 줄바꿈한다. 개발용 주문 표시, 권한 오류, 녹음 상태 등 실제 정보를 주는 안내는 유지한다. 제거 대상 문구의 빈 자리나 빈 `role="status"` 요소는 남기지 않는다.

## 2. 현재 구조와 변경 이유

- `VoiceOrderScreen.tsx`는 모든 녹음을 동일한 `/api/voice/interpret` 경로로 보내고 버튼의 목적을 전달하지 않는다.
- `backend/app/routers/voice.py`는 메뉴/추천 단계에서 규칙 기반 메뉴 해석이 `UNRECOGNIZED`이면 자동으로 LLM 추천을 호출한다. 메뉴명 없는 발화가 실제 추천 의도인지 별도로 확정하지 않는다.
- `OrderMicrophone.tsx`는 녹음 상태에 따라 단일 버튼을 표시한다. 버튼을 두 컴포넌트로 단순 복제하면 녹음 세션도 두 개 생겨 동시 녹음이 가능해질 수 있다.
- `OrderFooter.tsx`는 `status`를 항상 렌더링하고, 모바일 CSS는 하단 전체를 세로 배치한다. 안내의 선택적 표시와 내부 버튼 두 열 배치를 분리해야 한다.

버튼의 이름만 바꾸는 대신 요청 목적을 서버에 전달하여 주문과 추천 경로를 명확히 분리한다.

## 3. 사용자 흐름

| 상황 | 주문하기 | 메뉴 추천받기 |
| --- | --- | --- |
| 초기 화면 | 클릭 즉시 녹음 시작. 메뉴명·옵션을 듣고 직접 주문 경로로 해석 | 클릭 즉시 녹음 시작. 취향·조건을 듣고 추천 경로로 해석 |
| 메뉴명을 정확히 말함 | 메뉴 확인 화면으로 이동 | 바로 주문하지 않고 추천 결과로 표시. 해당 메뉴 요청도 추천 서비스의 기존 검증을 적용 |
| 메뉴명을 찾지 못함 | 메뉴명을 다시 말하거나 오른쪽 추천 버튼을 사용하도록 안내. LLM 추천을 자동 호출하지 않음 | 기존 LLM 추천을 호출하고 후보 또는 조건에 맞는 메뉴 없음 표시 |
| 추천 목록 표시 중 | 후보 메뉴명 또는 “첫 번째” 등으로 현재 후보 선택 | 새 조건을 녹음하여 새 추천 요청 |
| 빈 음성·무음 | 재입력 안내 | 재입력 안내. 빈 입력으로 LLM 호출하지 않음 |
| 메뉴 확인 이후 | 해당 단계의 단일 음성 입력 및 터치 선택 사용 | 두 버튼 표시 대상에서 제외 |

`주문하기`는 녹음을 시작하는 버튼이며 주문을 바로 저장하는 버튼이 아니다. 메뉴 확인과 최종 주문 확정을 반드시 유지한다.

초기 상단 안내는 “메뉴를 정하셨다면 주문하기를, 추천이 필요하면 메뉴 추천받기를 눌러 말씀해 주세요.”처럼 두 경로를 설명하도록 바꾼다. 하단의 “마이크를 누르고…” 문구와 음성 안내도 두 버튼의 실제 이름에 맞춰 갱신한다.

## 4. 구현 순서

### 4.1. 음성 요청 목적 계약 추가

구현 완료: `VoiceIntent`와 선택적 multipart `intent`를 추가했다. 주문 목적은 미인식 발화에서도 LLM을 호출하지 않고, 추천 목적은 메뉴명이 일치해도 추천 경로를 사용한다. 빈 입력·재추천 명령·옵션 보존·추천 검증·필드 생략 시 호환 동작을 유지하며, 부적절한 단계의 목적 필드는 전사 전에 거부한다. `backend/tests/test_voice_intent.py`에서 목적별 호출 횟수, 후보 제한, 오류, 커스터마이징 대기 상태, OpenAPI 선택적 enum 계약을 검증한다. 프론트 변경은 아직 없다.

- `/api/voice/interpret`의 multipart 필드에 `intent=order|recommend`를 추가한다. 현재 화면 단계인 `stage`와 녹음 목적을 구분한다.
- `intent`는 `menu` 또는 `recommendations` 단계에서만 허용한다. 이후 단계에서 보내면 `422 INVALID_VOICE_CONTEXT`, 정의하지 않은 값이면 스키마 검증 오류를 반환한다.
- 새 프론트는 두 버튼으로 녹음할 때 항상 `intent`를 보낸다. 이전 클라이언트와의 호환을 위해 필드가 없는 요청은 현재 자동 판별 동작을 유지하되, 신규 화면에서는 이 경로를 사용하지 않는다.
- `order`: 메뉴·후보 선택 규칙을 적용한다. `UNRECOGNIZED`도 `retry`로 반환하며 LLM 추천으로 넘어가지 않는다. 판매 중지·후보 밖 메뉴·잘못된 옵션 검증은 유지한다.
- `recommend`: 빈 전사를 먼저 거른 뒤 추천 서비스를 호출한다. 메뉴명 일치가 있더라도 `select_menu`로 바로 확정하지 않는다. 오류를 주문 경로로 대체하지 않는다.
- “다시 추천” 명령은 기존 `restart_recommendation` 초기화 행동을 유지한다. 구체적인 새 조건 녹음은 오른쪽 버튼으로 시작한다.
- 기존 `recognized_options` 계약을 그대로 사용한다. 추천 경로에서는 메뉴가 아직 선택되지 않았으므로 커스터마이징은 특정 메뉴에 조기 확정하지 않고 의도로 보존한다. 사용자 발화 온도와 LLM 후보 온도의 구분 및 제공 온도 검증도 유지한다.

### 4.2. 녹음 세션 하나로 두 버튼 제공

구현 완료: `VoiceIntentMicrophone`이 녹음 훅 하나로 두 버튼을 제공한다. 요청 ref의 동기 가드로 빠른 연속 클릭을 차단하고, 시작 시점의 목적 및 완료 콜백을 녹음 요청에 고정했다. 권한 요청/처리 중에는 두 버튼을 잠그며 녹음 중에는 활성 위치만 종료 버튼으로 바뀐다. 공통 상태 안내는 한 번 표시하고 오류 뒤 두 시작 버튼을 복구한다. 메뉴 확인 이후에는 기존 `OrderMicrophone`을 사용한다.

실제 버튼 동작을 검증할 수 있도록 화면에서 캡처한 `intent`를 전송하는 최소 연결도 추가했다. 새 추천 응답은 기존 옵션과 섞이지 않도록 새 세션에 적용한다. 목적과 다른 응답 행동 차단 및 목적별 안내 문구는 4.3에서, 기존 하단 안내 제거는 4.4에서 마무리한다. 이전 단계의 변경사항 및 스테이징 상태는 유지한다.

검증: 프론트 빌드, 단위 테스트 41개, 전체 Playwright 36개 통과. 추가한 브라우저 테스트는 같은 렌더 프레임의 양쪽 연속 클릭, 중복 종료, 녹음/처리 중 잠금, 전송 목적 고정, 권한 거부 후 목적 변경 재시도, 메뉴 확인 이후 단일 버튼 복귀, 권한 대기 중 이탈 시 트랙 해제를 검증한다. 가상 마이크와 mock API를 사용했다.

- `OrderMicrophone`을 확장하거나 별도 `VoiceIntentMicrophone`을 만들어 `useMicrophoneRecording` 인스턴스 하나를 공유한다. 단일 단계용 녹음 버튼도 기존처럼 지원한다.
- 버튼을 누르는 순간 `order`/`recommend` 목적을 녹음 세션의 ref에 고정한다. 녹음 종료 시 해당 값과 오디오를 함께 전달해 React 상태 갱신 시점에 따라 다른 목적으로 전송되지 않게 한다.
- 대기/완료/오류 상태에서는 두 시작 버튼을 표시한다. 오류 후에도 목적별 이름을 유지하고 오류 메시지를 별도로 표시한다.
- 권한 요청 중에는 두 버튼 모두 비활성화한다. 녹음 중에는 활성 버튼을 `녹음 종료`로 바꾸고 다른 버튼은 비활성화한다. 처리 중에도 두 버튼을 비활성화하고 활성 위치에 `음성 처리 중…`를 표시한다.
- 같은 버튼 연타·양쪽 빠른 클릭은 녹음 요청 하나만 생성한다. 권한 거부나 녹음 실패 후에는 두 시작 버튼을 다시 사용할 수 있게 한다.
- 녹음 시작 시 기존 TTS 중단, 화면 이동 시 녹음/업로드 취소, 언마운트 시 트랙 해제를 유지한다.

### 4.3. 화면·세션·응답 연결

구현 완료: `voice/voiceIntent.ts`에서 목적별 허용 행동과 재입력 안내를 정의하고, `VoiceOrderScreen`이 응답을 적용하기 전에 목적을 검사한다. 주문 요청에 추천 결과가 오거나 추천 요청에 직접 메뉴 선택이 오면 세션을 변경하지 않고 안내한다. 초기 화면·추천 목록의 상단 및 본문 설명도 두 버튼 이름에 맞췄다.

추천 성공 응답은 후보 구조·판매 여부·제공 온도·발화 온도와의 일치 여부를 확인한 뒤 새로운 옵션 세션으로 교체한다. `insufficient_data`는 빈 후보 배열일 때만 적용한다. HTTP 오류·잘못된 응답·추천 재입력·취소에서는 기존 후보와 옵션을 보존한다. 특히 추천 재입력에 포함된 `unresolved_fields`가 이전 주문 옵션을 무효화하지 않도록 수정했다. 후보를 음성/터치로 선택하고 확인할 때는 기존 추천 옵션을 유지한다.

검증: 빌드, 프론트 단위 테스트 43개, 전체 Playwright 46개 통과. 목적 불일치 응답 차단, 주문 미인식 안내, 새 추천의 옵션 교체, HTTP/재입력/잘못된 후보/불일치 빈 결과의 세션 보존, 음성 후보 선택→확인의 옵션 유지, 취소된 새 추천 응답 무시를 추가 검증했다. 가상 마이크·mock API를 사용했다.

- `VoiceOrderScreen.record`에 캡처한 요청 목적을 전달하고 multipart에 포함한다. 요청 ID/`revision` 및 `AbortController` 검사를 유지한다.
- `order` 요청에는 직접 메뉴/후보 선택 또는 재입력만, `recommend` 요청에는 추천 결과 또는 재입력만 허용한다. 예상하지 않은 행동을 받으면 화면을 진행하지 않고 안내한다. 초기화 행동은 두 경로에서 허용한다.
- 주문 목적의 실패 문구는 “메뉴 이름을 확인하지 못했어요. 다시 말씀하시거나 메뉴 추천받기를 눌러 주세요.”처럼 목적에 맞게 표시한다.
- 추천 후보를 주문하기로 선택할 때 기존 추천 조건과 인식 옵션을 유지한다. “네” 확인 및 터치 선택도 같은 세션을 사용한다.
- 새 추천 녹음 시작 시 이전 후보/옵션을 즉시 지우지 않는다. 정상 추천 응답을 적용할 때 새 추천 세션으로 교체하고 새 발화의 옵션만 보관한다. 실패·취소 시 기존 후보/옵션을 유지하며, 이전 발화의 포장·샷 등이 새 추천에 섞이지 않게 한다.
- 기존 `다시 추천받기` 버튼 및 “다시 추천” 음성 명령은 초기화 흐름을 유지한다. 홈 이동·새 주문 초기화와 늦은 응답 무시도 유지한다.
- 음성에서 선택된 온도·이용 방식·커스터마이징을 reducer에 전달하고 이미 선택한 화면을 생략하는 기존 기능을 회귀 검증한다.

### 4.4. 하단 레이아웃과 안내 정리

일반 음성 주문 화면에서 “음성 또는 터치로 주문해 주세요.” 문구와 해당 상태 요소를 제거했다. 개발용 주문 표시, 터치 주문 안내, 녹음 상태 메시지는 필요한 화면에 표시한다. 두 버튼은 같은 너비와 높이로 배치하며 작은 화면에서는 글자가 줄바꿈되고 마이크 아이콘의 크기를 줄인다.

320px·390px·1440px에서 버튼의 좌우 순서와 크기, 화면 넘침 및 콘텐츠 겹침 여부, 키보드 포커스 표시를 확인했다. 프론트 빌드, 단위 테스트 43개, 관련 브라우저 테스트 17개가 통과했다.

- `KioskLayout`/`OrderFooter`의 상태 안내를 선택적으로 렌더링하도록 변경한다. 일반 음성 주문 화면에서는 해당 안내를 전달하지 않고, 다른 화면의 상태 문구와 개발용 주문 안내는 유지한다.
- 두 버튼의 래퍼에 `grid-template-columns: repeat(2, minmax(0, 1fr))` 등 두 열 레이아웃을 적용한다. 기존 마이크 아이콘·버튼 스타일을 재사용한다.
- 데스크톱·모바일에서 버튼 높이, 터치 영역, 긴 문구 줄바꿈, 포커스 표시 및 하단 콘텐츠 가림 여부를 확인한다.
- 스크린리더 버튼 이름을 각각 `주문하기`, `메뉴 추천받기`로 제공하고, 비활성화 이유와 녹음 상태는 중복 안내 없이 전달한다.

### 4.5. 문서·검증

- API 문서에 요청 목적, 단계 제한, 필드 미전달 시 호환 동작, 목적별 응답 행동 표를 추가한다.
- 백엔드: 같은 발화가 주문/추천 목적에 따라 다른 경로로 처리되는지 검사한다. 주문 목적의 미인식 발화에서 LLM 호출 횟수가 0인지, 추천 목적의 정상 입력에서 1회인지, 빈 입력·잘못된 맥락에서 0인지 검증한다.
- 프론트: 녹음 시작 시 목적 고정, 단일 녹음 세션, 두 버튼 연타 방지, 새 추천 응답의 세션 교체, 실패 시 이전 선택 보존을 검사한다.
- Playwright: 초기 화면의 버튼 순서·아이콘·안내 제거, 목적별 전송 필드, 주문/추천 결과 차이, 권한 거부, 녹음 중 반대 버튼 비활성화, 이후 단계의 기존 입력을 검증한다.
- 기존 마이크/음성 주문/추천 테스트의 초기 진입 선택자를 새 버튼으로 변경한다. 메뉴 확인 이후 단일 녹음 버튼을 찾는 검증은 유지한다.
- 프론트 빌드·단위 테스트, 관련 백엔드 테스트, 전체 브라우저 회귀 테스트를 실행한다. 실제 마이크 검증 여부는 자동 테스트와 구분해 기록한다.

## 6. 완료 기준

- 초기 음성 화면과 추천 목록 하단에 왼쪽 `주문하기`, 오른쪽 `메뉴 추천받기`가 보이며 두 버튼 모두 기존 마이크 아이콘을 표시한다.
- `음성 또는 터치로 주문해 주세요.` 문구와 빈 안내 공간이 사라진다.
- 주문하기에서 “카페라떼 포장”을 말하면 메뉴 확인으로 이동하고 포장 옵션을 유지한다.
- 주문하기에서 메뉴를 특정할 수 없는 말을 해도 자동 추천으로 넘어가지 않는다.
- 메뉴 추천받기에서 “시원한 음료”를 말하면 추천 결과를 표시하고 COLD 선택을 유지한다.
- 메뉴 추천받기에서 메뉴명을 말해도 바로 주문 확인으로 이동하지 않고 추천 결과를 표시한다.
- 두 버튼 사이에 동시 녹음이나 응답 목적 혼선이 없고, 명시적 녹음 종료 후에만 분석을 요청한다.
- 메뉴 확인 이후 음성/터치 입력, 옵션 자동 선택·화면 생략, 최종 명시적 주문 확정이 정상 동작한다.
