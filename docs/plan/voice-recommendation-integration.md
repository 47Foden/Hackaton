## 1. 목표와 범위

실제 마이크로 등록 메뉴 또는 취향을 말한 뒤, 메뉴와 옵션을 선택해 기존 주문 흐름으로 결제 없이 접수하고 DB 주문번호를 표시한다. 메뉴 1개·수량 1개·HOT/COLD·매장/포장 규칙과 최종 **주문 확정** 버튼을 사용한다.

4단계의 음성 안내, 마이크 권한 처리, 녹음 시작·종료, 화면 이탈 시 트랙 해제를 이어받는다. `OrderScreen.applySelection`과 `orderReducer`는 터치 및 mock 음성 결과에서 이미 사용한다. 브라우저 녹음은 현재 업로드와 변환까지 연결돼 있으며, 변환된 오디오를 다음 구현에서 전사 요청에 연결한다. 운영 주문 저장은 기존 `POST /api/orders`와 요청 UUID 재시도 정책을 사용한다.

실제 전사와 추천은 이 후속 브랜치의 인수 항목이다. 기본 주문 브랜치의 인수 기준은 터치 주문·DB 저장·주문번호·4단계 마이크 조작까지다. 모델 추가 학습과 Pretuning 관리자 기능은 별도 범위다.

## 2. 구현 순서

### 5.1 실행 환경과 녹음 형식 확인

최종 운영에서는 공용 서버 한 대에 Whisper 가중치를 내려받아 미리 로드한 전사 프로세스를 상시 실행한다. 키오스크 브라우저는 공용 API에 녹음만 전송한다. Windows CPU 수치는 개발 기준선이다. 공용 서버에서 `large-v3`와 `large-v3-turbo`를 같은 한국어 샘플로 비교해 정확도와 녹음 종료부터 응답까지의 지연을 기준으로 모델을 선택한다.

- [x] 키오스크 브라우저·마이크와 Whisper 실행 장비를 정하고 환경을 기록한다. 지정 `large-v3-turbo`를 Windows 호스트의 CPU에서 실행해 한국어 합성 메뉴명·옵션 9개로 전사 정확도와 첫 실행·재호출 지연을 측정했다. [장비와 벤치마크 결과](whisper-benchmark.md)
- [x] Chrome `156.0.8078.81`의 합성 입력을 `audio/webm;codecs=opus` 그대로 업로드했다. Docker의 FFprobe `7.1.5`에서 WebM/Opus·48 kHz·모노를 검사하고, FFmpeg로 16 kHz 모노 PCM16으로 변환했다. 실제 디코딩 길이 2.76초의 변환 결과를 Windows의 `large-v3-turbo`에서 “아이스 아메리카노 주세요.”로 전사했다. [오디오 API 계약](../api-spec.md) · [FFmpeg 문서](https://ffmpeg.org/ffmpeg.html)
- [x] 녹음 형식과 크기·길이, 동시 처리 수 및 시간 예산을 정했다. 업로드·검사 경로에 제한을 적용했고, 초과 시 짧게 다시 녹음하도록 안내한다. 전사 시간 예산은 전사 API 연결 때 적용한다.

| 항목 | 초기 기준 | 근거 |
| --- | --- | --- |
| 허용 형식 | `.webm`의 `audio/webm;codecs=opus` 또는 `audio/webm`. 실제 WebM·Opus 오디오 트랙 하나 | 대상 Chrome에서 확인한 형식이며 브라우저가 보낸 MIME을 보존한다. |
| 최대 길이와 크기 | 30초·오디오 2 MiB. multipart 전체는 2 MiB + 16 KiB | 한국어 샘플은 1.90~2.76초이며, 여러 취향을 함께 말할 여유를 둔다. 30초 샘플은 317,804바이트였다. |
| 서버 동시 처리 | 음성 프로세스당 1건, 대기열 없이 추가 요청에 `503 AUDIO_BUSY` | CPU 기준 전사 재호출 중앙값 12.30초, 종료 시 프로세스 RSS 3.55 GiB를 고려해 한 건으로 시작한다. 초기 공용 서버는 음성 처리 워커 1개로 운영한다. |
| 업로드와 변환 | 업로드 수신 최대 5초. ffprobe 검사와 FFmpeg 변환을 합쳐 최대 5초 | 2.76초·30초 샘플을 각각 7회 변환했으며 전체 최대 176.1ms였다. |
| 전사 타임아웃 | 모델 로드 완료 후 최대 75초, 전사 API 연결 시 적용 | Windows CPU 워커의 전사가 기존 25초를 넘는 경우를 반영한다. |
| 클라이언트 타임아웃 | 업로드·검사 요청 15초, 전사 포함 요청 90초 | 서버의 업로드 5초·변환 5초·전사 75초에 네트워크 여유를 둔다. |

녹음이 제한을 넘으면 해당 녹음을 폐기하고 마이크를 해제한다. 화면에서 **다시 녹음**을 눌러 30초 이내로 발화하거나 터치 주문을 계속할 수 있다. 서버가 바쁘거나 처리 시간이 초과된 경우도 사용자가 다시 녹음한다. [세부 실측 결과](whisper-benchmark.md)

### 5.2 녹음 전송과 단계별 해석

- [x] 사용자가 **녹음 종료**를 누르면 마지막 `dataavailable`까지 모아 실제 MIME의 Blob을 만든다. 트랙을 해제한 뒤 비어 있지 않은 녹음만 `/api/voice/audio`로 보낸다. 단계 이동과 홈 이동은 업로드를 취소한다.
- [x] `POST /api/voice/interpret`의 multipart 필드, 반복 키 배열 인코딩, 성공·오류 응답을 [API 명세](../api-spec.md)에 확정했다. 오디오 검증·변환, 전사 워커 호출, 단계별 텍스트 해석을 분리했다.
- [x] 등록 메뉴명과 옵션을 현재 단계의 행동으로 변환한다. 등록 메뉴명 또는 현재 후보 순서가 명확하면 `select_menu`, 지원하는 취향 표현은 `recommend`, 빈 전사와 모호한 표현은 `retry`를 반환한다.

| 현재 단계 | 허용 행동과 검증 |
| --- | --- |
| 메뉴 선택 | `select_menu`, `recommend`, `retry`. 판매 중인 등록 메뉴만 선택한다. |
| 온도 선택 | `set_temperature`, `retry`. 해당 메뉴가 제공하는 HOT/COLD만 적용한다. 온도가 하나인 메뉴는 기존 자동 선택을 사용한다. |
| 매장/포장 | `set_service_type`, `retry`. DINE_IN 또는 TAKEOUT만 적용한다. |
| 추천 후보 | `select_menu`, `recommend`, `retry`. 선택은 현재 후보에 포함된 메뉴로 제한하고 재추천은 새 조건을 사용한다. |
| 최종 확인·전송·완료 | 주문 확정은 기존 버튼에서 수행한다. 음성 해석에서 이 단계의 주문 상태를 변경하는 행동은 정의하지 않는다. |

- [ ] 유효한 `select_menu`, `set_temperature`, `set_service_type` 결과는 터치 입력과 같은 선택 함수에 연결한다. 서버의 행동 검증에 더해 프론트에서도 현재 단계와 최신 메뉴·옵션을 확인한 뒤 기존 reducer를 호출한다.

#### 전사 워커 실행

기존 Whisper 벤치마크 가상 환경과 로컬 가중치를 사용한다. 저장소 루트에서 PowerShell을 열어 다음 명령으로 모델을 올린다. [벤치마크 환경 준비](whisper-benchmark.md)

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
& ./backend/scripts/voice/.venv/Scripts/python.exe -m app.services.voice.whisper_worker --model-dir models/whisper-large-v3-turbo --port 8765
```

FastAPI에는 `VOICE_TRANSCRIPTION_URL`을 지정한다. 같은 호스트에서 직접 실행할 때는 `http://127.0.0.1:8765/transcribe`, 로컬 Docker Desktop에서는 `http://host.docker.internal:8765/transcribe`를 사용한다. 공용 서버에서는 전사 워커를 사설 인터페이스에 둔다. `--model-dir`과 `--device`로 배포 모델과 CPU/CUDA를 선택한다. API가 75초 뒤 대기를 중단해도 워커는 진행 중인 전사를 마칠 때까지 새 요청에 `TRANSCRIPTION_BUSY`를 반환한다.

### 5.3 추천 데이터와 후보 화면

- [ ] Pretuning의 맛·분류 CSV를 입력 후보로 검토한다. `Pretuning` 브랜치의 CSV에는 이전 이름인 `레몬 아이스티`, `말차라떼`가 포함돼 있으므로 현재 카탈로그와의 대응을 검증한다. 매핑이 확정된 자료를 고정 `menu_id`로 변환하고, 필요한 항목은 재평가한다. 원본 CSV, 변환 내역, 데이터 버전을 구분한다.
- [ ] 현행 카탈로그 11종과 정확히 일치하는지, ID 중복·누락이 없는지, 분류는 0/1이고 맛 점수는 유한한 0~1 값인지 검증한다. 가격·판매 여부는 현재 메뉴 DB에서 읽는다. 검증을 마친 버전으로만 추천을 계산하며, 준비 전에는 `503 DATASET_NOT_READY`를 반환한다.
- [ ] `POST /api/recommendations`에서 검증된 조건으로 후보를 고른다. 초기 정책은 [API 명세의 추천 초안](../api-spec.md#66-post-apirecommendations)에 따라 종류·가격·판매 여부로 먼저 필터링하고, 지정한 맛 속성의 가중 거리로 최대 4개를 정렬하는 방식으로 검증한다. ‘달지 않은’은 단맛 목표를 낮게 두고, 동점은 `menu_id` 순으로 처리한다. 조합 조건의 해석과 조건에 맞는 후보가 없을 때의 안내를 테스트한다.
- [ ] 중앙에 후보의 메뉴명·사진·가격을 표시한다. 후보 선택은 공통 메뉴 선택 함수로 이어진다. **다시 추천받기**는 현재 후보를 지우고 새 취향을 입력받으며, 후보가 없거나 데이터가 준비되지 않으면 메뉴판으로 돌아갈 수 있게 한다.

### 5.4 실패 처리와 요청 수명주기

- [ ] 음성 요청마다 요청 ID와 제출 당시의 주문 세션·단계·선택 메뉴·후보 맥락을 기록한다. 화면이 바뀌거나 새 녹음을 시작하면 이전 요청을 취소하고, 이미 도착 중인 응답도 최신 요청 및 맥락이 일치할 때만 적용한다. 추천 응답에도 같은 검사를 적용한다.
- [ ] 권한 거부, 빈 녹음·무음, 모호한 결과, 지원하지 않는 형식, 타임아웃, 서버 장애, 추천 데이터 미준비를 각각 안내한다. 다시 녹음하거나 터치 주문을 계속할 수 있게 한다.
- [ ] 성공·실패·타임아웃 모두에서 임시 오디오와 변환 파일을 정리한다. 일반 운영 로그에는 요청 ID, 처리 시간, 실패 코드만 기록한다. 실제 녹음 원본과 전사 본문은 기본적으로 보관하지 않는다.

## 4. 인수 시나리오

| 시나리오 | 통과 기준 |
| --- | --- |
| 실제 메뉴 발화 | 실제 마이크로 ‘카페라떼’를 말하면 전사 후 등록 메뉴가 선택된다. 온도와 이용 방식을 음성·터치로 섞어 선택한 뒤 최종 확정하면 DB에 저장되고 같은 주문번호가 표시된다. |
| 실제 취향 발화 | ‘달지 않은 차’처럼 지원되는 조건을 말하면 검증된 데이터 버전에서 최대 4개가 표시된다. 후보를 선택해 주문할 수 있고, 재추천 시 새 조건으로 목록이 바뀐다. |
| 잘못된 입력 | 빈 발화, 모호한 메뉴명, 판매 중지 메뉴, 미지원 온도, 후보 밖 메뉴는 주문 초안을 변경하지 않는다. |
| 늦은 응답 | 녹음 후 단계 이동, 홈 이동, 연속 녹음, 추천 조건 변경을 재현해 이전 응답이 현재 주문을 변경하지 않음을 확인한다. |
| 장애와 회귀 | 타임아웃, 변환 실패, 권한 거부, 데이터 미준비에서도 터치 주문이 동작한다. 메뉴·옵션·추천 선택만으로 주문이 저장되지 않는다. |

완료 시 실제 장비·브라우저·Whisper 모델·데이터 버전과 테스트 결과를 기록한다. 자동 테스트는 합성 샘플과 대체 전사기로 실패 경로를 재현하고, 실제 마이크에서 전사와 주문 저장까지 이어지는 검증은 별도로 수행한다.
