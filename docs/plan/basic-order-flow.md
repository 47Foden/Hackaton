# 기본 주문 흐름 구현 계획

- 대상 브랜치: `feat/basic-order-flow`
- 작성일: 2026-11-07
- 상태: 기본 범위 확정. 공식 메뉴 매핑 및 가격 확인은 아래 결정 목록에서 관리한다.
- 이번 작업의 산출물은 구현 계획이며, 아래 API·DB·화면은 아직 구현하지 않았다.

## 1. 목표와 기준 문서

중앙 로고와 ‘주문하기’ 버튼에서 시작해, 안내·메뉴판·마이크가 있는 주문 화면으로 진입하고, 메뉴 선택 → 옵션 → 최종 확인 → 주문번호까지 연결한다. 터치와 음성은 같은 주문 상태와 저장 경로를 사용한다.

사용자 요청에 맞춰 계획은 `docs/plan/`에 둔다. 기존 `docs/plans/implementation-day1.md`는 팀 전체의 첫날 일정이며 이 브랜치의 범위 확정 문서로 사용하지 않는다.

| 문서 | 역할 |
| --- | --- |
| [프로젝트 개요](../project-overview.md) | 제품 흐름과 기존 MVP 범위 |
| [아키텍처](../architecture.md) | 화면·서버·음성·DB 책임 |
| [API 명세](../api-spec.md) | 메뉴·주문 계약과 후속 추천 초안 |
| [DB 설계](../db-design.md) | 테이블·제약·migration·seed 절차 |
| 이 문서 | 구현 순서, 단계별 산출물, 확인할 결정, 완료 기준 |

이 문서의 API·DB 제안은 합의 후 해당 기준 문서로 옮긴다. 같은 계약을 여러 문서에서 독립적으로 수정하지 않는다.

## 2. 현재 구현 상태와 범위

현재 프론트는 `frontend/src/main.tsx`에서 연결 상태만 표시한다. 백엔드는 `backend/app/main.py`의 `GET /api/health`만 구현돼 있다. Docker Compose로 React + Vite + TypeScript, FastAPI, PostgreSQL을 실행하며, 메뉴·주문 테이블, 초기 데이터, 실제 음성 인식은 없다.

### 요청 및 기존 기획에서 확인된 기준

- 시작 화면: 중앙 로고, 아래 ‘주문하기’ 버튼 하나.
- 주문 화면: 상단 텍스트·음성 안내, 중앙 간소화 메뉴판과 ‘메뉴판 보기’, 하단 마이크.
- 마이크를 누르면 안내 재생을 즉시 중단하고 녹음을 시작한다.
- 기존 기획상 녹음 종료는 사용자의 종료 버튼으로 처리한다. 상시 청취·무음 자동 종료는 포함하지 않는다.
- 메뉴 선택 후 HOT/COLD → 매장/포장 → 최종 확인을 거쳐 저장한다.
- 메뉴 1개·수량 1개, 실제 결제 없이 주문번호를 발급한다.
- PostgreSQL이 주문 기록의 원본이며, 저장 성공 후 DB 자동 증가 번호를 표시한다. 번호 초기화와 연속 무결번은 요구하지 않는다.

### 이번 브랜치의 확정 범위

1. 터치 주문을 실제 DB 저장까지 먼저 완성한다.
2. 음성 안내·녹음 조작과 음성/추천 API 연결 지점을 준비한다.
3. 실제 Whisper·추천 연결은 후속 브랜치로 분리한다.
4. 전체 메뉴판은 중앙 영역 안에서 확장하며, 다른 주문 단계로 넘어가기 전까지 유지한다. 상단 안내와 하단 마이크는 계속 보인다.

기존 개요는 메뉴별 제공 불가 옵션 처리·이전 단계 이동·옵션 변경·요청 ID 기반 중복 방지를 후속으로 두었으나, 첫날 일정 문서는 이를 포함하도록 제안한다. 사용자 답변에 따라 메뉴별 온도 제한 및 단일 온도 자동 선택은 이번 범위에 포함한다. 중복 방지는 후속으로 유지한다. 일정 문서의 제안을 확정 요구사항으로 간주하지 않는다.

## 3. 화면과 상호작용

### S0. 시작

- 로고를 화면 가운데 배치하고 바로 아래 주문하기 버튼을 둔다.
- 로고 파일이 없으면 개발용 텍스트 로고를 사용하고 최종 자산은 교체한다.
- 주문하기를 누르면 이전 주문 초안을 초기화하고 S1로 이동한다.
- 시작 화면에서 마이크 권한을 자동 요청하지 않는다.

### S1. 메뉴 선택

| 영역 | 구성과 동작 |
| --- | --- |
| 상단 Inform | ‘마이크 버튼을 눌러 음성 주문과 추천을 받을 수 있습니다.’ 텍스트 및 안내 재생 |
| 중앙 기본 | 메뉴 사진·이름·가격 카드와 메뉴판 보기 버튼. 간소화 목록의 선정 기준은 결정 필요 |
| 중앙 확장 | 전체 메뉴와 큰 카드/글씨 표시. 내부 스크롤로 탐색하며 선택 전까지 확장 상태 유지 |
| 하단 | 이름이 있는 마이크 버튼, 녹음/처리 상태와 짧은 조작 안내 |

- 메뉴판 보기는 별도 팝업보다 중앙 영역 확장을 우선 제안한다. 축소 버튼 제공 여부는 사용자 확인 후 결정한다.
- 메뉴 선택 시 확장 메뉴판 대신 옵션을 중앙에 표시한다. 추천 결과도 중앙 영역에서 표시한다.
- 메뉴 로딩·조회 실패·목록 없음은 각각 구분한다. 조회 실패 시 다시 불러오기 버튼을 제공한다.
- 사진이 없거나 이미지 로딩이 실패해도 이름·가격·선택 버튼은 사용할 수 있어야 한다.

### S2. 온도 선택 / S3. 매장·포장

- 선택 메뉴와 가격을 표시하고 단계별로 큰 선택 버튼을 제공한다.
- 온도를 고르면 매장·포장 단계로, 이용 방식을 고르면 최종 확인으로 진행한다.
- 기본 구현은 온도와 이용 방식만 지원한다. 크기·얼음·샷·당도 변경은 별도 합의 대상이다.
- 공식 메뉴 기준으로 제공 온도를 제한하고 서버도 검증한다. 온도가 하나이면 해당 값을 자동 설정하고 온도 질문을 생략해 매장/포장으로 이동한다. 두 가지이면 온도 선택을 표시한다. 제공 온도가 없거나 미확정이면 주문을 막는다.
- 이전 단계 이동과 옵션 재선택은 현재 기획상 후속이다. 포함 결정 시 메뉴 변경에 따른 하위 옵션 초기화까지 함께 구현한다.

### S4. 최종 확인 / S5. 주문 완료

- 메뉴, 온도, 이용 방식, 수량 1, 합계와 주문 확정 버튼을 표시한다.
- 주문 확정은 사용자가 버튼으로 실행한다. 음성 인식 결과로 자동 저장하지 않는다.
- 전송 중 확정 버튼을 비활성화하고 진행 상태를 표시한다.
- 성공 응답을 받은 경우에만 주문번호를 크게 표시한다. 이 단계는 결제 완료를 뜻하지 않는다.
- 완료 화면의 ‘처음으로’는 새 주문을 위해 선택값·인식 결과·오류·메뉴판 확장 상태를 모두 초기화한다. 자동 복귀 시간은 이번 기본값에 넣지 않는다.

## 4. 프론트 상태와 음성 수명주기

화면 단계는 `start | menu | temperature | service_type | review | submitting | complete`로 분리하는 것을 제안한다. 추천 연결 시 `recommendations`를 추가한다. 녹음 상태는 화면 단계와 독립적으로 `idle | requesting_permission | recording | processing | error`로 관리한다.

주문 초안은 `menuId`, `temperature`, `serviceType`만 유지하고 표시 가격은 메뉴 조회 결과에서 찾는다. 주문 결과는 서버가 반환한 ID·번호·확정 금액으로 관리한다. 터치와 음성 모두 `selectMenu`, `setTemperature`, `setServiceType` 같은 공통 상태 변경 함수를 호출한다.

### 마이크 입력 순서

1. 클릭 즉시 현재 안내와 대기 중인 안내를 취소한다. 권한 요청이나 녹음 준비 완료까지 기다리지 않는다.
2. 마이크 권한을 요청하고, 허용되면 녹음을 시작한다.
3. 녹음 중에는 버튼을 ‘녹음 종료’로 바꾸고 안내 음성을 재생하지 않는다.
4. 종료 버튼을 누르면 녹음을 마치고 녹음 장치 트랙을 해제한다.
5. 실제 연결 모드에서는 파일과 현재 주문 맥락을 서버로 전송한다. mock 모드는 개발용임을 명시한다.
6. 응답에 따라 메뉴·옵션·추천 또는 재입력 상태를 표시한다.

- 안내 방식은 브라우저 TTS를 우선 제안하되 실제 한국어 음성과 실행 브라우저에서 검증한다. 지원되지 않으면 텍스트 안내로 계속 주문할 수 있다.
- 음성 안내 내용은 화면 단계 진입 시 갱신하며 리렌더마다 반복 재생하지 않는다.
- 권한 거부·녹음 장치 없음·보안 환경 제한·인식 실패를 구분해 안내한다. 마이크 실패가 터치 주문을 막지 않는다.
- 화면 이동·새 주문·컴포넌트 정리 시 안내, 녹음, 처리 중 요청을 정리한다. 이전 단계의 늦은 음성 응답은 요청 식별자와 단계 확인으로 무시한다.
- 네트워크 요청 취소가 서버의 작업 취소를 보장하지는 않는다. 특히 주문 요청은 음성 조회와 다르게 취급한다.

## 5. API 계약 제안

아래 메뉴·주문·음성 API는 신규 제안이다. 실제 구현 전 `docs/api-spec.md`에 필수 값·오류·예시를 확정한다. 프론트는 `/api` 상대 경로로 호출한다.

### 5.1 메뉴 조회 — `GET /api/menus`

```json
{
  "menus": [
    {
      "menu_id": "peach_iced_tea",
      "name": "복숭아 아이스티",
      "price_krw": 3000,
      "image_url": null,
      "is_available": true,
      "display_order": 1,
      "is_featured": true
    }
  ]
}
```

- 위 가격은 형식 설명용이며 확정 판매 가격이 아니다. 기존 명세의 11개 메뉴 ID를 재사용한다.
- `is_featured`로 간소화 목록을 구성하는 방안을 제안한다. 개수·선정 목록은 미정이며 ID를 프론트에 중복 하드코딩하지 않는다.
- 이미지 URL은 없으면 null로 두고 공통 대체 이미지를 표시한다.
- 판매 불가 메뉴는 선택을 막는다. `available_temperatures`를 필수로 추가하고 조회·검증·DB를 함께 구현한다. 공식 ICE 표기는 API의 COLD로 변환한다.
- 가격 없는 데이터는 개발 fixture에서만 허용하고, 실제 주문 저장 대상 메뉴는 확정된 정수 원화 가격을 가져야 한다.

### 5.2 주문 저장 — `POST /api/orders`

```json
{
  "menu_id": "peach_iced_tea",
  "temperature": "COLD",
  "service_type": "TAKEOUT"
}
```

성공 `201` 응답 제안:

```json
{
  "order_id": "1",
  "order_number": "1",
  "menu_id": "peach_iced_tea",
  "menu_name": "복숭아 아이스티",
  "temperature": "COLD",
  "service_type": "TAKEOUT",
  "quantity": 1,
  "total_price_krw": 3000,
  "created_at": "2026-11-07T09:00:00+09:00"
}
```

- 온도는 `HOT | COLD`, 이용 방식은 `DINE_IN | TAKEOUT`. 수량은 서버에서 1로 고정한다.
- 클라이언트가 가격을 결정하지 않는다. 서버가 메뉴·판매 여부·지원하는 옵션을 검증하고 가격을 조회해 저장한다.
- `order_id`는 내부 식별자, `order_number`는 화면 표시 값이다. MVP에서는 같은 DB 증가값을 사용하고 JSON에는 문자열로 반환하는 방안을 제안한다.
- 없는 메뉴는 `404 MENU_NOT_FOUND`, 판매 불가는 `409 MENU_UNAVAILABLE`, 허용되지 않은 옵션은 `422 INVALID_OPTION`, DB 장애는 `503 ORDER_STORAGE_UNAVAILABLE`을 제안한다.
- 오류는 기존 API 문서의 `detail.code/message` 형식을 따른다. 필수 필드·자료형 오류는 FastAPI 기본 422와 구분한다.

### 5.3 저장 실패와 중복 정책

기존 MVP처럼 서버 중복 방지를 제외하면 프론트의 버튼 잠금만으로 동시 요청·새로고침·응답 유실에 따른 중복을 막을 수 없다.

- 입력 검증 등 저장되지 않았음이 명확한 실패는 수정 후 재제출할 수 있다.
- 타임아웃·연결 끊김 등 저장 여부가 불명확한 경우 자동 재전송하지 않는다. ‘주문 접수 여부를 확인해 주세요’ 상태를 표시한다.
- 접수 확인에 관리자/DB 확인이 필요한 제한이 남는다. 사용자가 중복 방지를 후속으로 확정했으므로 이번 범위에는 포함하지 않는다.
- 포함 시 UUID `request_id`, DB UNIQUE 제약, 동일 ID·동일 내용의 기존 결과 반환, 다른 내용의 `409 IDEMPOTENCY_CONFLICT`, 동시 요청 처리와 재시도 검증까지 하나의 작업으로 추가한다.

### 5.4 후속 음성·추천 연결

- `POST /api/voice/interpret`: multipart `audio`와 맥락 필드 `stage`, `selected_menu_id`, `candidate_menu_ids`를 보내는 방안. 배열 직렬화 형식도 계약에서 명시한다.
- 응답 제안: `transcript`, `action`. 행동은 `select_menu`, `set_temperature`, `set_service_type`, `recommend`, `retry`로 나누고 종류별 필수 필드를 정의한다.
- 단계에 맞지 않는 행동이나 현재 추천 후보 밖의 메뉴 응답은 적용하지 않는다.
- 녹음 MIME, 변환 위치, 크기·길이 제한, 처리 타임아웃은 실제 브라우저·Whisper 실행 환경 확인 후 결정한다. 파일 확장자를 MP3로 바꾸는 것은 변환이 아니다.
- `recommend`는 해석된 조건을 반환하고 프론트가 기존 초안의 `POST /api/recommendations`를 호출하는 방안을 제안한다.
- 추천 데이터 미준비는 기존 명세의 `503 DATASET_NOT_READY`로 표시한다. 예시 점수를 실제 추천 결과로 사용하지 않는다.
- 추천 순위·부정 조건·후보 부족 처리는 개요와 상세 API 초안 사이에 차이가 있어 실제 연결 전에 한 규칙으로 확정한다.

## 6. DB 설계 제안

직접 SQL과 현재 `psycopg`를 활용하는 최소 구성을 제안한다. 새 ORM은 필수로 도입하지 않는다. 합의 후 `docs/db-design.md`에 DDL·관계·제약·실행 절차를 기록한다.

| 테이블 | 주요 필드 | 제약 및 의미 |
| --- | --- | --- |
| `menus` | `menu_id TEXT`, `name TEXT`, `price_krw INTEGER`, `image_url TEXT NULL`, `is_available BOOLEAN`, `display_order INTEGER`, `is_featured BOOLEAN` | menu_id PK, 가격 NOT NULL 및 0 이상, 이름 필수 |
| `orders` | `id BIGINT GENERATED ALWAYS AS IDENTITY`, `menu_id TEXT`, `menu_name_snapshot TEXT`, `unit_price_krw INTEGER`, `temperature TEXT`, `service_type TEXT`, `quantity INTEGER`, `total_price_krw INTEGER`, `created_at TIMESTAMPTZ` | id PK, menu_id FK, enum CHECK, quantity = 1, 금액 0 이상, 합계 = 단가 × 수량 |

- 단일 메뉴 주문이므로 초기에는 `order_items` 없이 한 행에 저장한다. 다품목 도입 시 별도 설계한다.
- 주문 시점 이름과 가격을 스냅샷으로 저장해 메뉴 변경 후에도 주문 이력을 유지한다. 주문에서 참조된 메뉴는 삭제하지 않고 판매 중지로 관리한다.
- 주문번호는 `orders.id`에서 얻는다. 별도 날짜별 카운터 테이블이나 일일 초기화를 추가하지 않는다.
- 메뉴 검증·가격 읽기와 주문 INSERT는 하나의 트랜잭션으로 처리한다. 판매/가격 변경과 주문의 동시성 처리 기준을 SQL 구현 시 정한다.
- DB에 COMMIT된 후에만 성공을 반환한다. JSON·CSV 파일에 주문을 이중 저장하지 않는다.
- 초기 데이터는 기존 11개 ID를 기준으로 재실행 가능한 seed로 관리한다. 명시적 seed 실행 시 갱신할 항목을 정하고 앱 시작마다 운영 메뉴를 덮어쓰지 않는다.
- 추천 속성표 가격 정책과 판매 메뉴 가격 정책은 충돌 여부를 먼저 확인한다. 실제 가격을 기존 허용 집합에 맞추기 위해 임의 반올림하지 않는다.
- 기존 Docker 볼륨에도 적용되도록 버전 순서가 있는 SQL migration과 적용 기록을 둔다. 새 DB 초기화 스크립트만으로 기존 DB 갱신을 대신하지 않는다.
- seed·migration 스크립트는 현재 `backend/app` 볼륨 경로 안에 두는 구성을 우선 제안한다. 다른 경로 사용 시 Dockerfile/Compose 포함 여부를 함께 확인한다.

## 8. 권장 파일 구성

아래는 신규 경로 제안이며 미리 모든 파일을 만들 필요는 없다. 기능 규모에 맞춰 분리한다.

```text
frontend/src/
  main.tsx                      # 앱 마운트
  App.tsx                       # 단계와 화면 연결
  components/                   # 안내, 메뉴 카드/메뉴판, 마이크
  screens/                      # 시작, 메뉴, 옵션, 확인, 완료
  state/order.ts                # 주문 상태와 전이
  api/                          # 공통 타입, 메뉴·주문 호출, 개발 mock
  hooks/                        # 안내 재생과 녹음 수명주기
  styles/                       # 레이아웃과 접근성 스타일
backend/app/
  main.py                       # 앱과 라우터 등록, health 유지
  routers/menus.py
  routers/orders.py
  schemas/                      # 메뉴·주문 요청/응답 모델
  services/orders.py            # 검증·저장 트랜잭션
  db/                           # 연결, migration, seed 실행
  data/menu_catalog.json        # 합의한 초기 메뉴
backend/tests/                  # 실제 주문 검증·저장 통합 검사
docs/plan/basic-order-flow.md
```

실제 음성·추천을 포함할 때 관련 라우터와 서비스를 추가한다. 로고·메뉴 이미지는 Vite에서 제공 가능한 자산 경로를 정하고 Docker 실행 및 빌드 결과에서도 접근되는지 확인한다.

## 9. 검증 및 인수 시나리오

| 시나리오 | 통과 기준 |
| --- | --- |
| 첫 진입 | 중앙 로고와 주문하기 버튼 하나 표시 |
| 주문 화면 진입 | 위 안내·중앙 간소화 메뉴·아래 마이크 표시 |
| 전체 메뉴판 | 중앙에서 확대되고 다른 조작 없는 리렌더로 접히지 않음. 안내·마이크 접근 가능 |
| 터치 주문 | 메뉴 → 온도 → 이용 방식 → 최종 확인 → 실제 저장 → 번호 표시 |
| 확정 시점 | 메뉴·옵션 선택만으로는 저장되지 않고 최종 버튼으로만 요청 |
| 주문 검증 | 잘못된 메뉴/옵션 거부, 서버 가격 사용, 잘못된 요청은 저장되지 않음 |
| 저장 실패 | 성공 번호를 꾸며 표시하지 않음. 미확인 결과는 자동 재전송하지 않음 |
| 다음 고객 | 처음으로 이동 후 이전 메뉴·옵션·인식·번호·오류가 남지 않음 |
| 안내 중단 | 마이크 클릭 즉시 음성 안내 및 재생 대기 취소 |
| 녹음 실패 | 권한 거부/장치 없음에서도 터치 주문 가능 |
| 자원 정리 | 화면 이동 후 마이크 트랙 해제, 이전 음성 결과가 새 주문을 변경하지 않음 |
| 환경 재현 | 새 DB migration/seed 및 기존 DB migration 가능, frontend 빌드 성공 |
| 실제 음성·추천 (포함 시) | 실제 전사·메뉴/옵션 선택·추천·재입력 후 주문 저장까지 가능 |
| 중복 방지 (포함 시) | 같은 request_id의 동시 요청·재전송이 한 행/같은 번호, 다른 내용은 409 |

DB 저장·유효성·롤백·서버 가격 계산은 자동 통합 검사로 확인한다. 음성 해석을 포함하면 단계별 발화 해석을 테스트한다. 버튼 표시만 확인하는 테스트를 늘리기보다 실제 화면 흐름과 API/DB 결과를 연결해 확인한다.

고령층 대상 화면이므로 큰 글씨·명확한 대비·넓은 터치 영역을 사용한다. 아이콘에 텍스트 이름을 붙이고 상태를 색만으로 전달하지 않는다. 키보드 포커스, 상태 안내, 작은 화면/확대 시 중앙 스크롤과 하단 버튼 접근도 확인한다.

| D8 | 안내 재생은 브라우저 TTS로 가능한가? 음성 실행 장비·브라우저는? | 단계 4 전 확인. 실제 음성 포함 시 MIME·변환·제한도 단계 5 전에 확정 |
| D9 | 이전 단계 이동·옵션 변경도 필요한가? | 기존 기획은 후속. 포함 시 상태 초기화·뒤로가기 정책을 단계 1 전에 확정 |

위 표는 최초 질문 목록이다. 아래 확정 기록이 우선하며, 이미 답변한 사항을 다시 질문하지 않는다.

## 11. 최신 메뉴 데이터 결정

- Pretuning에서 가져온 common의 기존 파일 구조와 11개 항목을 유지한다.
- 사용자 요청대로 레몬 아이스티는 레몬티, 말차라떼는 녹차라떼로 변경한다. 레몬티와 레몬차는 동일 공식 상품이지만 항목은 합치지 않는다.
- 가격은 common/menu_prices.json, 출처는 common/menu_price_sources.json을 기준으로 한다. 공식 홈페이지에 가격이 없어 매장 주문 페이지와 에스프레소 모바일쿠폰 가격을 사용했다.
- 공식 메뉴 이미지 14개는 frontend/public/images/menus에 저장했다. common/menu_images.json의 메뉴명·HOT/COLD로 연결하고 원본 URL은 common/menu_image_sources.json에 보관한다.
- 실제 제공 온도는 이미지 매핑의 키와 공식 출처를 기준으로 한다. 하나뿐이면 온도 질문을 생략한다.
- PRICE_OPTIONS는 새 가격 집합으로 수정했다. 앞부분의 미확정 가격·기존 11개 ID 관련 제안보다 이 절과 common/README.md가 우선한다.
- 터치 주문·DB 저장·주문번호를 먼저 구현하고 실제 음성·추천과 중복 방지는 후속으로 둔다. 중앙 메뉴판 확대 유지, 단일 메뉴·수량 1, 결제 없음과 DB 증가 번호 정책도 유지한다.

## 12. 브랜드 디자인 확정

사용자 결정에 따라 공식 메가MGC커피 로고를 사용하고 이후 프론트 디자인은 공식 사이트와 비슷한 스타일로 진행한다. 상세 기준과 자산 준비 상태는 [프론트 디자인 기준](../frontend-design.md), 로고·색상 출처는 [브랜드 자산](../../common/brand_assets.json)에 기록했다. 간소화 목록은 아직 선정 전이며, 출처·준비 상태 정리 완료가 목록 선정 완료를 뜻하지 않는다.

## 13. 메뉴판 표시 구현

간편 목록은 프로젝트 초기 설정으로 아이스아메리카노·카페라떼·복숭아 아이스티·레몬에이드 4종을 사용한다. 인기 순위나 공식 추천으로 표시하지 않는다. common/menu_display.json에서 목록과 순서를 변경한다. 가격·온도·이미지는 기존 common 원본에서 읽는다.

전체 메뉴판은 11종이며 목록 모드와 확대 여부를 독립적으로 관리한다. 선택·리렌더·간편/전체 전환으로 확대 상태나 선택 메뉴를 초기화하지 않는다. ‘처음으로’로 주문 화면을 나갔다 새 주문에 진입하면 초기 간편/기본 크기로 돌아간다. 간편 목록 밖에서 선택한 메뉴도 선택을 유지하며 전체 목록에서 확인 가능하다고 안내한다.

## 14. 개발용 주문 흐름 연결

메뉴 선택 → 제공 온도 선택(단일 온도는 자동 선택) → 매장/포장 → 최종 확인 → 개발용 완료 화면을 연결했다. screens/order에는 단계별 화면, state/order.ts에는 단계별 전이와 옵션 검증, components/order에는 공통 요약을 둔다. 선택 온도에 맞는 common 이미지를 사용한다.

사용자가 개발용 확정 버튼을 누를 때만 완료 화면으로 진행한다. DEV-DEMO는 고정 예시이며 실제 주문번호가 아니다. API 호출·DB 저장·결제를 수행하지 않는다. 처음으로 돌아가 새 주문을 시작하면 주문 초안과 메뉴판 표시 상태가 초기화된다. 이전 단계 이동·옵션 변경은 기존 범위대로 후속이다.

검증: npm --prefix frontend run build, npm --prefix frontend test. 두 온도 선택, HOT/COLD 전용 자동 선택, 조기 확정 및 단계에 맞지 않는 옵션 거부를 확인한다. Node 22.18 이상 또는 프로젝트 Docker의 Node 24에서 테스트를 실행한다.

## 15. API 어댑터 분리 완료

메뉴·주문 요청은 KioskApi 인터페이스로 통일하고 화면은 useMenus/useOrderFlow를 통해 사용한다. common 참조는 mock 카탈로그로 이동했다. 주문 전이는 submitting → 성공 응답 → complete이며 오류는 review로 돌아간다. 완료 화면은 응답 번호·이름·가격·옵션을 사용한다.

기본 모드는 mock이고 실제 저장되지 않는 DEV- 번호를 반환한다. VITE_API_MODE=http로 변경하면 같은 계약의 HTTP 어댑터를 사용한다. 실제 백엔드 메뉴/주문 구현 완료를 뜻하지 않는다. 시나리오와 실행 설정은 frontend/src/api/README.md를 따른다. 기존 고정 DEV-DEMO는 mock 응답의 DEV- 번호로 대체했다.

메뉴 로딩·오류·빈 목록, 주문 진행·명확한 거부·접수 불명 상태를 제공한다. 성공 응답 전 완료 화면으로 이동하지 않으며 접수 불명 오류는 자동 재시도하지 않는다. 실제 서버 연동과 mock 계약/오류 검증은 구분한다.


## 16. 메뉴 DB 기반 구현 완료

명시적 migration/seed CLI, common 사전 검증, 연결 컨텍스트, 메뉴 조회 repository를 구현했다. 현재 개발 DB에 메뉴 11개를 seed했고, PostgreSQL의 별도 테스트 스키마에서 신규/재실행·보존·제약·롤백 테스트 5개를 통과했다. 실행법은 backend/app/db/README.md를 따른다. GET /api/menus 및 프론트 HTTP 전환은 아직 후속 체크리스트다.


## 17. 실제 메뉴 조회 전환

조회 모드 기본값은 http, 주문 모드는 아직 mock이다. createKioskApi에서 두 연결을 조합하며 조회 실패 시 fixture로 대체하지 않는다. 개발용 주문도 실제 응답의 판매 상태·온도·가격을 사용한다. 로컬 Vite와 Docker의 프록시 주소를 분리했다. 설정법은 frontend/src/api/README.md에 기록했다. 테스트 14개, 타입 검사·빌드·Compose 설정 및 실행 중 프론트의 Vite 프록시→실제 DB 메뉴 조회를 확인했다.

## 18. 메뉴 조회 상태 검증 완료

frontend/e2e/catalog.spec.mjs에서 실제 Chromium과 HTTP 응답 제어를 사용해 다음을 확인했다. 실제 DB 데이터를 변경해서 장애를 만들지 않고 브라우저 테스트에서만 API/이미지 응답을 재현한다.

| 상태 | 검증 결과 |
| --- | --- |
| 로딩 | 응답 대기 중 안내 표시, 메뉴 카드 없음, 처음으로 접근 가능 |
| 실패 | HTTP 503 안내와 재조회 버튼 표시, 재조회 성공 시 메뉴 복구. 작은 화면 가로 넘침 없음 |
| 빈 목록 | HTTP 200의 빈 menus는 실패와 별개로 안내, 재조회로 복구 |
| 이미지 404 | 카드와 주문 요약에 사진 준비 중 표시. 메뉴명·가격 유지, 선택·옵션·확정 버튼 사용 가능 |
| 빈 이미지 경로 | 깨진 img 대신 대체 표시, 주문 선택 가능 |

CatalogStatus는 조회 상태 UI를, MenuImage는 이미지 실패/빈 경로 처리를 공통으로 담당한다. 이미지 주소가 바뀌면 이전 실패 상태도 초기화한다. API 자체의 잘못된 카탈로그는 백엔드 검증 규칙대로 503으로 처리하며, 이미지 파일 로딩 실패는 터치 주문을 막지 않는다.

재현: npm --prefix frontend run test:e2e. 최초 실행 전 frontend에서 npx playwright install chromium을 실행한다. 테스트는 별도 Vite 포트 5177에서 조회 http/주문 mock을 강제하며 실제 백엔드 접속 없이 상태를 재현한다.
