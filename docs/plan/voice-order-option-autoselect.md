# 음성 주문 옵션 자동 선택 및 단계 생략 구현 계획

- 작성일: 2026-11-10
- 작업 브랜치: `feat/voice-order-option-autoselect`
- 현재 단계: 1번 발화 옵션 추출·응답 계약과 2번 음성 세션 옵션 보존 구현 완료. 2번의 원자적 옵션 적용에 필요한 3번 reducer 전이도 연결했으며, 전체 인수 기준 검증 및 실제 마이크 확인은 후속 작업

## 목표와 범위

음성 주문에 온도·이용 방식·샷·시럽 등 커스터마이징 옵션이 포함되면 선택값을 보존하고 해당 선택 화면을 생략한다. 메뉴 확인과 최종 주문 확정은 유지한다. 범위는 HOT/COLD, DINE_IN/TAKEOUT 및 선택 메뉴·온도에서 실제 제공하는 커스터마이징 옵션이다.

온도·이용 방식은 미선택 항목만 질문한다. 커스터마이징은 현재 여러 그룹을 한 화면에서 선택하는 선택 사항이므로, 발화에서 지정한 커스터마이징을 모두 유효하게 해석했다면 해당 화면 전체를 생략하고 언급하지 않은 그룹은 기본 상태(추가 선택 없음)를 유지한다. 예를 들어 “샷 추가”만 말해도 샷 선택을 보존하고 시럽·사이즈를 추가로 묻지 않는다. “추가 옵션 없이”도 명시적 선택 완료로 처리한다. 커스터마이징을 전혀 언급하지 않았으면 기존 화면을 표시한다. 모호하거나 지원하지 않는 요청이 남았다면 화면을 생략하지 않고 유효한 선택을 미리 표시한 상태로 확인받는다.

프로젝트의 아이스 값은 `ICE`가 아니라 `COLD`다. “시원한 음료”는 `COLD`, “따뜻한 음료”는 `HOT`, “포장”, “가져갈게요”는 `TAKEOUT`, “매장에서”, “먹고 갈게요”는 `DINE_IN`으로 정규화한다.

## 현재 구조와 원인

- `backend/app/services/voice/interpretation.py`: 현재 단계의 단일 행동을 반환한다. 옵션은 온도·이용 방식 단계에서 전체 발화가 사전에 일치할 때만 인식하며, 메뉴와 옵션이 섞인 발화는 처리 범위가 좁다.
- `backend/app/schemas/voice.py`: 메뉴 선택 행동에 옵션 정보가 없다. 추천 후보의 `temperature`는 존재하지만 사용자 발화로 확정된 값인지 구별하지 않는다.
- `backend/app/routers/voice.py`: 규칙으로 메뉴를 해석하지 못하면 LLM 추천으로 연결한다. 이 경로에서도 발화 옵션을 별도로 전달해야 한다.
- `frontend/src/screens/VoiceOrderScreen.tsx`: 추천 후보의 ID만 저장하고, 메뉴 확인 후 `select_menu`에 메뉴만 전달한다.
- `frontend/src/state/order.ts`: 단일 온도 메뉴만 자동 선택한다. 온도 선택 후 커스터마이징을 거쳐 항상 이용 방식 화면으로 이동한다.
- `frontend/src/screens/order/CustomizationScreen.tsx`: 여러 옵션 그룹을 한 화면에 표시하고 선택값은 빈 배열로 시작한다. 보존된 선택을 초기값으로 받을 수 있어야 한다. 현재 음성 화면은 커스터마이징 단계에서 마이크를 비활성화한다.

## 구현 순서

### 1. 발화 옵션 추출과 응답 계약

구현: `backend/app/services/voice/options.py`에서 카탈로그 기반 의도 추출·검증을 수행하고, 기존 음성 행동과 함께 선택적 `recognized_options`를 반환한다. 메뉴·온도 미확정은 `pending`, 모호한 표현은 `needs_clarification` 또는 `unresolved_fields`로 구분한다. API 문서와 `backend/tests/test_voice_options.py`에 계약 및 검증 사례를 추가했다.

`VoiceInterpretResponse`에 선택적 `recognized_options`를 추가한다. 내부 필드는 `temperature?: HOT | COLD`, `service_type?: DINE_IN | TAKEOUT`로 정의하고, 미인식 항목은 생략한다. 기존 `action` 구조를 유지하며 구버전 응답에 필드가 없어도 기존 흐름이 동작하게 한다.

커스터마이징은 `customization?: { status: 'resolved' | 'pending' | 'needs_clarification', option_ids: string[], intents: ..., unresolved: ... }`로 확장한다. 필드 부재는 미언급, `resolved`와 빈 배열은 명시적인 “추가 옵션 없이”를 뜻한다. `intents`에는 메뉴·온도가 정해지기 전에도 유지할 정규화된 요청(샷 수, 시럽 종류 등)을, `unresolved`에는 확인할 표현을 담는 타입을 정의한다. 메뉴·온도 확정 전에는 `pending`으로 보관하고 실제 제공 옵션에 매핑한 뒤에만 `resolved`로 전환한다.

`common/order_option_profiles.json`과 메뉴 API의 `option_groups`를 기준으로 “샷 추가” → `shot:extra`, “2샷 추가” → `shot:double` 등의 동의어를 매핑한다. 시럽도 실제 제공되는 종류와 ID로만 매핑하며 “시럽 추가”가 여러 종류를 가리키면 확인을 요청한다. 존재하지 않는 ID나 임의 수량을 생성하지 않는다. 중복 ID, 그룹별 `max_selections`, 메뉴·온도별 제공 여부를 검증한다. “샷 추가 말고 연하게” 같은 정정은 같은 그룹의 기존 값을 교체하고 다른 그룹의 선택은 유지한다. 유효한 선택이 일부 있어도 미해결 요청이 남으면 화면 생략 조건을 충족하지 않는다.

전사 문자열에서 옵션을 한 번 추출하고 메뉴 직접 선택·추천·추천 후보 선택·메뉴 확인·옵션 선택 경로에서 공통으로 사용한다. 단순 부분 문자열 일치로 부정 표현을 확정하지 않는다. “핫 말고 아이스”처럼 명확한 정정은 최종 의도를 반영하고, “핫이나 아이스”, “안 시원한 것”처럼 확정하기 어려운 표현은 자동 선택하지 않는다. 서로 충돌하는 값으로 이전 선택이 조용히 확정되지 않도록 충돌 필드를 별도로 전달하거나 해당 발화를 재입력 처리한다.

메뉴와 옵션이 섞인 “아이스 카페라떼 포장해 주세요”도 직접 메뉴 선택으로 처리한다. 옵션을 제거하더라도 메뉴 이름 자체의 “아이스”와 여러 메뉴를 비교·부정하는 문장을 손상하지 않도록 기존 메뉴 판별과 함께 검증한다.

사용자가 말한 온도와 LLM이 추천 결과에 채운 온도를 분리한다. 온도를 말하지 않았다는 이유만으로 LLM의 후보 온도를 사용자 선택으로 간주하지 않는다. “시원한 음료 추천”은 `recognized_options.temperature=COLD`를 추천 응답에도 포함한다. 추천 결과가 해당 온도를 제공하는지는 실제 메뉴 데이터로 확인한다.

### 2. 음성 주문 세션의 옵션 보존

구현: `frontend/src/state/voiceOptions.ts`에서 응답 검증·필드별 병합·메뉴/온도별 재검증을 수행한다. `VoiceOrderScreen`은 추천과 확인 사이에서 원래 의도를 보존하고, reducer에는 세션 전체 스냅샷을 전달한다. 커스터마이징 화면의 초기 선택 및 음성 입력을 연결하고, 재추천·홈 이동·언마운트 시 옵션/요청을 정리한다. 모호한 커스터마이징은 유효한 선택을 표시한 상태에서 화면의 계속 버튼으로 명시적으로 확인할 수 있다.

검증: 프론트 단위 테스트 26개, 음성 백엔드 테스트 42개 및 프론트 빌드 통과. 브라우저 테스트는 추천→터치 선택→음성 확인→최종 요청의 옵션 보존, 재추천 초기화, 미해결 옵션 표시, 늦은 응답 무시와 기존 음성 주문 회귀를 다룬다. STT/LLM 응답은 mock을 사용한다.

`VoiceOrderScreen`에 현재 추천·메뉴 선택 과정의 인식 옵션을 보관한다. 추천 카드의 터치 선택이나 “첫 번째”, 메뉴 확인의 “네”에서도 유지하고, 새 발화에서 명확히 지정한 필드만 갱신한다.

메뉴 확인 시 검증한 옵션을 `select_menu`와 함께 reducer에 전달한다. “네, 포장이요”처럼 확인과 옵션이 함께 있는 발화도 지원한다. 온도 단계의 “아이스로 포장” 역시 온도 적용과 이용 방식 예약을 하나의 전이로 처리한다.

“아이스 카페라떼 샷 추가하고 포장”, “네, 샷도 추가해 주세요”, “샷 추가 가능한 시원한 음료 추천”의 커스터마이징 의도를 추천·메뉴 확인·온도 선택까지 보존한다. 메뉴 또는 온도가 변경되면 원래 의도를 해당 메뉴·온도의 옵션으로 다시 검증한다. 지원하지 않는 선택을 조용히 삭제하거나 다른 옵션으로 대체하지 않고, 유효한 선택은 유지한 채 확인할 항목을 안내한다.

커스터마이징 화면이 필요한 경우 보존된 옵션을 초기 선택값으로 전달한다. 이 단계에서도 음성으로 옵션을 지정할 수 있도록 마이크를 활성화하고, 백엔드 `VoiceStage`에 `customization`, 요청 맥락에 선택 메뉴·온도, 행동 계약에 `set_options`를 추가한다. 메뉴 확인 단계에서도 메뉴·온도가 알려져 있으면 검증 맥락을 전달할 수 있도록 라우터의 현재 맥락 제한을 갱신한다. 유효한 커스터마이징 발화를 적용하면 같은 화면에서 재확인하지 않고 다음 미선택 단계로 이동한다.

다시 추천받기·새 주문·홈 이동은 인식 옵션을 초기화한다. 같은 추천 목록에서 다른 후보를 고르는 동안에는 요청 조건을 유지하되 새 메뉴의 지원 온도를 다시 검증한다. 선택 메뉴가 요청한 온도를 제공하지 않으면 안내하고 다시 선택하게 하며, 반대 온도로 조용히 대체하지 않는다.

기존 `revision`과 요청 취소 검사를 유지하여 늦게 도착한 응답이 새 주문의 옵션을 덮어쓰지 않게 한다.

### 3. reducer에서 다음 미선택 단계 계산

`OrderAction.select_menu`에 선택적 초기 옵션을 추가하고, 중간 상태에 미리 선택한 이용 방식·커스터마이징 의도·검증된 선택값·해결 상태를 보존한다. 온도와 커스터마이징 단계에서 복합 옵션을 적용할 수 있는 행동도 정의한다. 빈 옵션 배열만으로 미언급과 선택 완료를 판단하지 않는다. 일반 터치 주문은 옵션을 전달하지 않아 기존 동작을 유지한다.

다음 단계 계산을 공통 함수로 모은다.

1. 유효한 온도가 있으면 사용하고, 없으면 기존 단일 온도 자동 선택 또는 온도 화면으로 이동한다.
2. 해당 온도에서 커스터마이징 의도를 검증한다. 모두 해결됐다면 `selectedOptions`를 구성하고 커스터마이징 화면을 생략한다. 미언급 상태이고 제공 옵션이 있거나 확인할 요청이 남았다면 화면을 표시하며 기존 선택과 예약된 이용 방식을 유지한다. 제공 옵션이 없어도 사용자가 지원하지 않는 옵션을 요청했다면 안내·확인 없이 통과시키지 않는다.
3. 커스터마이징 완료 또는 불필요한 경우, 이용 방식이 이미 있으면 `review`로 이동하고 없으면 `service_type`으로 이동한다.

여러 `dispatch`나 화면 진입 후 effect로 단계를 연속 통과시키지 않고 한 번의 reducer 전이에서 목적 단계를 결정한다. 이를 통해 생략할 화면과 음성 안내가 잠깐 노출되는 현상도 방지한다. 주문 확인 화면과 최종 요청에는 실제 선택된 온도·이용 방식·커스터마이징 값을 표시하고 전달한다.

### 4. 계약 문서와 검증

- `docs/api-spec.md`: 응답 필드, 복합 발화, 미인식·충돌·지원하지 않는 옵션 처리 예시를 추가한다.
- 백엔드 테스트: 동의어, 메뉴+옵션, 추천+옵션, 확인+옵션, 부정·정정·충돌, 지원하지 않는 온도, 옵션 미언급을 검증한다. STT/LLM은 mock하여 발화 해석과 응답 계약을 재현 가능하게 검사한다.
- `frontend/tests/order.test.mjs`: 두 옵션/온도만/이용 방식만/둘 다 없음의 단계 전이, 커스터마이징을 거치는 옵션 보존, 유효하지 않은 값, 기존 터치 주문을 검사한다.
- `frontend/e2e/voice-order.spec.mjs`: 생략 대상 화면 및 해당 음성 안내가 발생하지 않는지, 추천→터치 선택→메뉴 확인에서도 옵션이 남는지, 최종 요청값이 정확하고 확정 전 주문이 전송되지 않는지 검증한다.
- 커스터마이징 검증: 샷·시럽 복합 발화, 일부 그룹만 언급했을 때 전체 화면 생략, 명시적 옵션 없음과 미언급의 구분, 같은 그룹 정정, 중복·선택 개수 초과, 메뉴·온도 변경 후 재검증, 모호한 시럽 종류를 검사한다. 미해결 요청이 있을 때 유효한 선택이 화면에 남는지, 커스터마이징 단계의 음성 입력 후 이동도 확인한다.
- 주문 결과 검증: 생략한 커스터마이징의 `option_ids`가 최종 요청에 포함되고, 확인 화면 및 서버 주문 결과의 선택 내역·추가 금액·총액이 일치하는지 검사한다. 샷만 지정했을 때 다른 그룹에 임의 옵션이 추가되지 않아야 한다.
- 관련 백엔드 테스트, 프론트 단위 테스트, `npm run build`, 관련 Playwright 시나리오를 실행한다. 실제 마이크로 “시원한 음료 포장해 주세요”도 수동 확인한다.

| “아이스 카페라떼 포장해 주세요” | 메뉴 확인 → 커스터마이징(있는 경우) → 주문 확인. COLD/TAKEOUT |
| “시원한 음료 추천해 줘” | 추천 → 메뉴 선택·확인 → 커스터마이징(있는 경우) → 매장/포장. 온도 재질문 없음 |
| “카페라떼 매장에서 마실게요” | 메뉴 확인 → 온도 → 커스터마이징(있는 경우) → 주문 확인. DINE_IN 보존 |
| “카페라떼 주세요” | 기존 온도·커스터마이징·매장/포장 흐름 |
| 온도 단계에서 “아이스로 포장” | 커스터마이징(있는 경우) → 주문 확인. 매장/포장 재질문 없음 |
| “아이스 카페라떼 샷 추가하고 포장” | 메뉴 확인 → 주문 확인. 온도·커스터마이징·매장/포장 화면 생략, COLD/shot:extra/TAKEOUT 및 추가 금액 보존 |
| “카페라떼 샷 추가” | 메뉴 확인 → 온도 → 매장/포장 → 주문 확인. 커스터마이징 화면 생략, 나머지 그룹은 추가 선택 없음 |
| 제공되는 샷·시럽을 함께 지정 | 두 선택을 모두 보존하고 커스터마이징 화면 생략, 각 추가 금액 반영 |
| “아이스 카페라떼 추가 옵션 없이 포장” | 메뉴 확인 → 주문 확인. 커스터마이징 선택 완료 및 빈 선택값 보존 |
| 커스터마이징 단계에서 “샷 추가하고 포장” | 샷과 이용 방식 적용 후 주문 확인. 추가 선택 확인 화면 없음 |
| “샷 추가하고 시럽도”에서 시럽 종류가 모호함 | 샷 선택을 유지한 커스터마이징 화면에서 미해결 시럽 확인, 화면 생략하지 않음 |
| 명확하지 않거나 제공하지 않는 옵션 | 임의 확정 없이 안내·재입력 또는 해당 옵션 선택 |
| 재추천·새 주문 | 이전 인식 옵션이 다음 주문으로 유출되지 않음 |

## 작업 시 유의사항

브랜치 생성 시 이미 있던 라우터·음성 워커·테스트·문서 및 별도 worktree의 변경은 보존한다. 구현 때 현재 변경사항과 충돌하는 부분을 확인하고 필요한 범위만 수정한다. 2번 구현은 세션 보존, 커스터마이징 음성 API 확장 및 해당 값을 주문 상태로 전달하는 전이까지 포함한다.
