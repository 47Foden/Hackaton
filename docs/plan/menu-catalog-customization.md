# 메뉴 확장 및 추가 옵션 구현 계획

## 1. 범위와 데이터 기준

- 요청 목록 43종을 카탈로그에 반영한다. 기존 메뉴와 겹치는 9종은 같은 `menu_id`로 갱신하고, 신규 34종은 고정 ID를 부여한다. 목록 외 기존 `에스프레소`와 `레몬티`는 유지하는 전제로 주문 가능 카탈로그 45종을 구성한다. 기존 `iced_americano`는 표시명을 `아메리카노`로 바꾸고 기존 ID와 음성 별칭을 유지한다. `레몬티`와 `레몬차`의 기존 ID도 유지한다.
- 기본가와 추가금은 이번에 전달받은 원화 금액을 사용한다. 공식 메뉴명, 온도, 사진은 메가MGC커피 공식 메뉴 상세에서 메뉴별로 확인한다. 카탈로그의 가격 출처는 사용자 제공 값으로 기록하고, 이미지 출처와 분리한다.
- [공식 메뉴](https://www.mega-mgccoffee.com/menu/)의 음료 목록과 상세를 대조해 제품명, HOT/ICE 구분, 온도별 공식 원본 이미지 URL, 상세 출처, 확인일을 기록한다. 확인한 이미지는 기존 `frontend/public/images/menus/` 경로에 저장한다. 상품명이 다른 경우 매핑을 기록하고, 출처나 온도를 확인하지 못한 항목은 보류 목록에 남겨 주문 화면 노출 전에 해결한다. 목록 첫 페이지나 사진 모양으로 제공 온도를 결정하지 않는다. 예를 들어 전달 목록의 딸기라떼는 `ice/hot`이지만 [공식 딸기라떼 표기](https://www.mega-mgccoffee.com/menu/menu.php?category=6&menu_category1=1&menu_category2=1&page=1)는 ICE이며, 기존 프로젝트의 공식 이미지 매핑도 COLD만 등록되어 있다.
- 이전 옵션 작업 트리의 `docs/menu-options-research.md`와 후보 JSON은 출처 조사 자료로 활용한다. 이전 문서의 화면 순서는 이번 요구에 맞춰 온도 → 추가 옵션 → 매장/포장으로 적용하고, 옵션 구성과 가격은 이번 입력을 기준으로 삼는다.

## 2. 카탈로그와 옵션 데이터

현재 `common/`의 가격·온도별 이미지 구조를 확장한다. 주문 메뉴 ID·카테고리·옵션 프로필 연결은 별도의 공유 카탈로그에 두고, 백엔드 시드와 프런트엔드 모의 API가 같은 데이터를 읽도록 한다. `pretuning.py`가 사용하는 `common/menu_data.py`의 점수 평가용 메뉴와 분류는 보존한다. 카탈로그 로더의 11종 고정 검사와 DB의 카테고리 제약을 갱신한다. 전체 메뉴는 커피·디카페인·음료의 하위 분류로 찾을 수 있게 하고, 간편 화면의 대표 메뉴 설정은 유지한다.

모든 메뉴에 **사이즈업 +700원**을 제공한다. 요청 목록의 각 하위 그룹은 첫 메뉴를 기준으로 옵션 프로필 하나를 공유한다. 온도와 기본가는 메뉴별로 관리하고, 같은 종류의 추가 옵션도 프로필별 가격을 저장한다.

| 디카페인 · 라떼 | 디카페인 카페라떼 | 디카페인 샷, 우유 변경, 당도 |

| 음료 · 티 | 복숭아 아이스티 | 논커피용 샷, 당도 |

각 그룹·선택지에 고정 ID, 표시명, 원화 추가금, 정렬 순서, 최대 선택 수를 둔다. 예를 들어 바닐라 시럽은 카페라떼 그룹에서 +700원, 콜드브루 오리지널 그룹에서 +500원이다. 디카페인 아메리카노와 디카페인 카페라떼의 샷 가격도 별도로 유지한다.

초기 구현 가정은 다음과 같다.

- 카페라떼의 `샷 선택`은 일반 아메리카노의 연하게 0원, 1샷 추가 +600원, 2샷 추가 +1,200원을 사용한다. 일반 연하게, 콜드브루 연하게, 휘핑/휘핑 제외처럼 추가금이 생략된 선택지는 0원으로 처리한다.
- 그룹마다 미선택 또는 한 항목을 선택할 수 있고, 서로 다른 그룹의 선택지는 함께 적용한다. 시럽 등 한 그룹에서 여러 개를 고르는 규칙이 정해지면 해당 프로필의 최대 선택 수만 조정할 수 있게 한다. `샷 추가`와 `2샷 추가`, `휘핑 제외`와 `젤라또 변경`은 같은 그룹에서 동시에 선택할 수 없다.
- 티 그룹에 나열된 제로 복숭아 아이스티, 사과유자차 등에도 복숭아 아이스티의 옵션 프로필을 적용한다. 목록 외 기존 2종은 공통 사이즈업만 제공한다.

## 3. 주문 화면과 상태 전이

| 공식 제공 온도 | 화면 순서 |
| --- | --- |
| HOT과 ICE 모두 | 메뉴 → 온도 → 추가 옵션 → 매장/포장 → 주문 확인 |
| ICE만 또는 HOT만 | 메뉴 → 해당 온도 자동 확정 → 추가 옵션 → 매장/포장 → 주문 확인 |

- 기존 공용 주문 상태에 `customization` 단계를 추가한다. 터치 주문과 음성 주문에서 메뉴·온도 선택이 끝나면 같은 상태 전이와 옵션 화면을 사용한다. 이번 범위의 옵션 선택은 터치로 제공하며, 추가 옵션 단계의 음성 안내는 화면에서 선택하도록 안내한다. 기존 메뉴·온도·매장/포장 음성 인식은 이어서 동작한다.
- 선택한 메뉴·온도에 연결된 그룹만 표시하고, 초기 선택은 비워 둔다. **옵션 없이 계속**할 수 있으며, 옵션별 추가금과 합계를 바로 갱신한다. 다른 메뉴나 온도로 바뀌면 새 조합에서 유효하지 않은 옵션은 제거한다.
- 주문 확인과 완료 화면에 온도, 매장/포장, 옵션명, 추가금, 최종 금액을 표시한다. 완료 화면은 서버가 저장한 주문 결과를 사용한다.

## 4. API, 저장 및 추천

- `GET /api/menus`에 메뉴·온도별 적용 가능한 옵션 그룹과 추가금을 포함한다. `POST /api/orders`는 선택지 ID 목록만 입력받고, 생략된 목록은 빈 선택으로 처리한다. 서버는 메뉴의 판매 상태, 온도, 선택지 소속, 중복 및 그룹 최대 선택 수를 확인한 후 `기본가 + 선택지 추가금 합계`를 계산한다. 모의 API에도 같은 검증과 계산을 적용한다.
- 새 DB 마이그레이션에서 카탈로그 옵션과 주문 시점 옵션 스냅샷을 저장한다. 주문 생성과 옵션 스냅샷을 같은 트랜잭션에서 저장하고, 기존 주문은 빈 옵션으로 읽는다. 같은 `request_id`의 재시도는 옵션 ID 집합까지 비교해, 순서만 다른 같은 선택이면 저장된 결과를 반환하고 선택이 다르면 기존 충돌 응답을 사용한다.
- `common/recommendation/`의 두 CSV와 출처 파일, `outputs/taste-only/`의 원본 점수표는 유지한다. 현재 `load_scores()`는 점수표 행이 전체 `MENU_IDS`와 일치해야 하므로, 메뉴만 추가하면 기존 추천도 실패한다. 점수표 검증 범위를 기존 스냅샷에 매핑된 메뉴 ID로 분리하고, 추천은 그중 현재 판매 가능한 메뉴를 대상으로 계산한다. 신규 메뉴는 전체 메뉴 탐색과 음성 이름 주문에서 선택할 수 있고, 맛 추천 후보에는 점수가 연결된 메뉴만 포함한다. 아메리카노의 기존 점수는 `iced_americano`로 연결해 표시명 변경 후에도 사용한다.

## 5. 구현 순서와 완료 기준

1. 요청 43종을 목록으로 대조하고, 공식 상품명·온도·사진 매핑과 사용자 지정 가격을 채운다. 중복 ID, 출처 없는 이미지, 파일 누락, 온도 불일치가 없는지 검증한다.
2. 옵션 프로필, 카탈로그 시드, DB 마이그레이션과 메뉴·주문 API를 연결한다. 기존 DB 업그레이드, 옵션 미선택 주문, 잘못된 옵션 거절, 정상 추가금 계산 및 재시도를 확인한다.
3. 터치·음성 주문에 공용 옵션 화면을 붙이고, HOT/ICE 메뉴와 단일 온도 메뉴가 각각 올바른 순서로 진행되는지 확인한다. 예를 들어 카페라떼에 사이즈업·오트밀크·바닐라 시럽을 고르면 `2,900 + 700 + 500 + 700 = 4,800원`이 주문 확인과 저장 결과에 일치해야 한다.
4. 기존 맛 추천이 확장 카탈로그에서도 동작하고, 점수 없는 신규 메뉴가 일반 주문에는 표시되며 추천 계산은 실패하지 않는지 확인한다. 점수 CSV와 출처 파일이 변경되지 않았는지 최종 diff로 검증한다.
