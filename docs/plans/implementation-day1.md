# 구현 첫날: 3인 작업 계획

> 이전 구현 계획입니다. 현재 45종 LLM 직접 추천의 실행·구조는 [현재 안내](../llm-direct.md)를 따릅니다. 이 문서의 CSV/Pretuning 제안은 현재 구현에서 제거됐습니다.

작성일: 2026-11-07. 담당자 이름은 A/B/C에 배정하세요. 아래 새 API·필드·시간 배분은 아직 팀 합의나 구현 완료를 뜻하지 않습니다.

## 1. 오늘의 목표와 구현 순서

**가장 먼저 터치로 주문번호까지 받는 흐름을 완성하고, 같은 흐름에 음성 입력과 추천을 붙입니다.**

1. 메뉴·옵션·주문·음성 해석의 입력과 출력 형식을 합의합니다. 
2. 화면, 주문 서버, 음성·추천을 동시에 만듭니다.
3. 메뉴 조회 → 터치 선택 → 옵션 → 확인 → DB 저장 → 주문번호를 연결합니다.
4. 음성 → 텍스트 → 메뉴/옵션 선택을 같은 화면 상태에 연결합니다.
5. 취향 → 추천 → 선택을 연결하고 실패·재시도를 점검합니다.

현재 코드에는 연결 확인 화면과 `GET /api/health`만 있습니다. `api-spec.md`는 추천 속성표 생성·추천의 초안이고, `db-design.md`는 비어 있습니다. 서비스가 이미 구현되어 있다는 전제로 작업하지 않습니다.

오늘의 필수 도착점은 **실제 DB에 저장되는 터치 주문과 실제 녹음으로 메뉴를 선택하는 경로**입니다. 추천까지 연결하는 것을 목표로 하되, 모델 환경·검색 근거·가격 확정 상황에 따라 별도 완료 여부를 기록합니다. 터치만 동작하거나 가짜 음성 결과를 연결한 상태를 전체 MVP 완료로 표시하지 않습니다.

## 2. 3명의 역할과 파일 소유권

| 담당 | 책임 | 주로 수정할 경로(신규 경로는 제안) | 독립 개발 방법 | 인수할 결과 |
| --- | --- | --- | --- | --- |
| A — 화면·사용자 흐름 | 시작/메뉴/추천/옵션/확인/완료 화면, 주문 상태, 녹음, 안내 중단 | `frontend/` | 공통 예시 응답을 반환하는 mock API로 개발 | 터치와 음성이 같은 상태 변경 함수를 사용하고, API 연결만 바꿔 실제 서버로 전환 |
| B — 메뉴·주문·DB·통합 | 메뉴 원본, 초기 데이터, 주문 검증/저장/중복 방지, API 조립 | `backend/app/main.py`, `backend/app/routers/menus.py`, `backend/app/routers/orders.py`, `backend/app/services/orders.py`, `backend/app/db/`, `backend/data/menu_catalog.json` | 프론트 없이 API 요청과 DB로 검증 | 메뉴 API와 실제 주문번호 발급, 동일 요청 재전송 시 중복 없음 |
| C — 음성·해석·추천 | Whisper 어댑터, 단계별 발화 해석, 추천 계산, 속성표 생성 준비 | `backend/app/routers/voice.py`, `backend/app/routers/recommendations.py`, `backend/app/services/voice/`, `backend/app/services/recommendation/`, `backend/scripts/pretuning/` | 녹음 샘플·텍스트·검증용 속성표로 함수와 라우터 검증 | 실제 음성 인식 결과 및 공통 행동 응답, 추천 API |

DB만 한 명에게 맡기면 프론트와 음성 연동을 맡은 사람이 과부하됩니다. B가 메뉴·주문을 세로로 완성하고, C는 DB 없이도 호출 가능한 음성·추천 함수부터 만듭니다.

공통 파일은 소유자를 정합니다.

- B: `compose.yaml`, 백엔드 `Dockerfile`, `requirements.txt`, `main.py`, 공통 스키마와 메뉴 원본. C는 필요한 라이브러리·실행 조건을 B에게 전달합니다.
- A: 프론트 의존성, 화면 진입점, 프론트 API 어댑터.
- C: 모델 실행 설정과 추천 산출물. 모델 파일·원본 녹음·키는 Git에 넣지 않습니다.
- C는 독립된 `APIRouter`를 내보내고 B가 `main.py`에서 등록합니다. 두 사람이 진입점을 동시에 수정하지 않습니다.
- 처음 계약 합의 때 B가 `api-spec.md`와 `db-design.md`를 정리합니다. 이후 형식 변경은 소비하는 담당자에게 먼저 알리고 예시도 함께 바꿉니다.

## 3. 처음 40분에 같이 정할 것

이 단계의 짧은 의존성은 필요합니다. **의존성을 없애는 것이 아니라, 서로의 완성 코드를 기다리는 시간을 없애는 방식**입니다.

### 0~15분: 데모와 데이터 고정

- 한 번에 메뉴 1개, 수량 1개. 결제·다품목·추가 학습은 오늘 작업에 넣지 않습니다.
- 기존 API 문서의 11개 `menu_id`를 그대로 사용합니다.
- 메뉴별 가격, HOT/COLD 가능 여부, 판매 가능 여부를 확정합니다. 모델이 가격을 추정하거나 프론트가 임의로 정하지 않습니다.
- 가격이 미정이면 테스트 전용 데이터임을 표시해 개발을 계속하되, 실제 추천 데이터 게시와 최종 데모 전에는 확정합니다. 기존 허용 가격 집합과 실제 가격이 충돌하면 정책을 먼저 결정합니다.
- 오늘 사용할 PC·마이크·브라우저와 Whisper 실행 장비를 정합니다. 녹음 종료는 우선 버튼 방식, 음성 안내는 브라우저 지원 여부를 확인해 한 방식으로 정하는 것을 제안합니다.

### 15~40분: 연결 규격과 공통 예시 확정

다음 표는 **합의할 최소 계약 제안**입니다. 승인한 내용은 `api-spec.md`에 반영하고 이 계획을 두 번째 API 명세로 사용하지 않습니다.

| 연결 지점 | 최소 합의 내용 | 생산자 → 소비자 |
| --- | --- | --- |
| `GET /api/menus` | `menu_id`, 이름, `price_krw`, `available_temperatures`, 판매 가능 여부, 이미지 경로 또는 null | B → A/C |
| `POST /api/orders` | 요청: `request_id`, `menu_id`, `temperature`, `service_type`. 응답: `order_id`, `order_number`. 수량은 1로 고정 | A → B |
| `POST /api/voice/interpret` | multipart 음성 파일 + 현재 `stage` + 선택 메뉴 ID + 추천 후보 ID 목록. 응답: `transcript`와 행동 결과 | A → C |
| `POST /api/recommendations` | 기존 API 문서의 filters/targets/weights/limit와 응답을 사용. 자연어는 C가 먼저 조건으로 변환 | A → C |
| 음성 행동 결과 | `select_menu`, `recommend`, `set_temperature`, `set_service_type`, `retry`의 종류와 종류별 필수 값 | C → A |

함께 정할 세부 규칙:

- 온도는 `HOT`/`COLD`, 이용 방식은 `DINE_IN`/`TAKEOUT` 등 하나의 표기로 통일합니다.
- 단계는 `menu`/`recommendations`/`temperature`/`service_type` 등 하나의 표기로 통일합니다. ‘첫 번째’는 전달받은 추천 목록 안에서만 해석합니다.
- `recommend` 행동은 추천 API가 받을 조건을 반환하도록 제안합니다. 프론트가 조건으로 추천 API를 호출하고, 메뉴 이름·이미지는 메뉴 목록에서 ID로 찾습니다.
- 빈 발화·모호한 발화는 `retry`로 안내합니다. 모델 실행 장애는 별도 오류로 처리합니다. 인식 결과만으로 주문을 확정하지 않습니다.
- 지원 녹음 MIME 형식, 파일 크기·길이 제한, 처리 시간 초과, 마이크 권한 거부 UI를 정합니다. 브라우저 출력 형식이 모델 입력과 다르면 C가 서버 변환을 담당합니다.
- 같은 주문 ID와 같은 내용은 기존 주문을 반환하고, 같은 ID에 다른 내용은 충돌 오류로 반환합니다. 응답 유실 후 재시도는 같은 ID를 사용합니다.

B가 `contracts/examples/`에 성공·실패 JSON 예시를, `backend/app/schemas/`에 서버 스키마를 만드는 것을 제안합니다. A는 이 예시로 프론트 타입·mock을 만들고, C도 같은 형식으로 반환합니다. **공통 준비는 40분 안에 끝내고, 예시가 준비된 영역부터 착수합니다.**

## 5. 서로를 기다리지 않게 만드는 구체적인 방법

### A는 서버 완성을 기다리지 않습니다

화면에서 직접 `fetch`를 흩어 쓰지 않고 `frontend/src/api/`에 모읍니다. 동일 함수의 mock 구현과 실제 API 구현을 교체합니다. mock에서도 로딩·오류·빈 추천·주문 재시도를 재현합니다. 메뉴·음성 선택 모두 `selectMenu(menuId)` 같은 동일 상태 변경 경로로 들어갑니다.

### B는 화면이나 음성을 기다리지 않습니다

API 문서 화면 또는 요청 스크립트로 메뉴 조회와 주문 저장을 검증합니다. 주문 테이블은 요청 ID의 유일 제약과 트랜잭션으로 중복을 막습니다. 자동 증가 주문번호는 연속 무결번을 보장할 필요가 없습니다. 서버가 메뉴·가격·제공 옵션을 검증합니다.

초기 데이터 입력은 재실행해도 메뉴가 중복되지 않게 만듭니다. 팀원마다 별도 DB이므로 수작업으로 넣은 데이터만으로 진행하지 않습니다.

### C는 DB와 프론트를 기다리지 않습니다

처음부터 세 부분을 나눕니다.

1. `transcribe(audio) → text`: Whisper 어댑터.
2. `interpret(text, context, catalog) → action`: 단계별 해석.
3. `recommend(criteria, dataset) → ranked_menu_ids`: 추천 계산.

2와 3은 모델 없이 문자열·예시 데이터로 검증할 수 있습니다. 1은 실제 녹음으로 따로 검증합니다. B의 메뉴 DB가 완성되기 전에는 합의한 카탈로그 파일을 사용하고, 이후 같은 형태의 메뉴 데이터를 전달받습니다.

추천 계산의 검증용 숫자는 실제 맛 평가 결과와 분리합니다. 데이터셋이 준비되지 않으면 운영 API는 기존 명세대로 `DATASET_NOT_READY`를 반환하고, 테스트 모드만 예시를 사용합니다.

**남는 실제 의존성:** 주문은 확정 메뉴/옵션과 DB에, 음성 데모는 실행 가능한 모델에, 실제 추천은 근거·가격이 완성된 속성표에 의존합니다. mock은 개발 대기를 줄일 뿐 이 완료 조건을 대신하지 않습니다.

## 6. 오늘 우선순위를 낮출 작업과 막혔을 때의 대응

- **Whisper 추가 학습:** 기존 모델로 실제 인식부터 연결합니다. 추가 학습은 별도 일정입니다.
- **관리 API·관리 화면 전체:** 오늘 핵심 주문 흐름보다 후순위입니다. 기존 설계를 삭제하지 말고 속성표 생성은 우선 별도 실행 스크립트로 진행하는 방안을 합의합니다.
- **5회 맛 평가:** C의 병렬 준비 작업으로 두되, 검색 근거·가격·키가 준비되기 전에는 실행 완료로 간주하지 않습니다. 키가 없는 현재 상태에서는 파서·검증·집계 코드와 테스트 자료를 먼저 준비할 수 있습니다.
- **음성 실행이 2시간째에도 안 됨:** GPU/모델 로딩/오디오 변환 중 원인을 구분하고 지원되는 실행 환경을 결정합니다. 텍스트 입력으로 해석 기능 개발은 계속하되, 음성 기능은 미완료로 기록합니다.
- **추천 데이터가 6시간째에도 미완성:** 메뉴명 음성 주문·터치 주문을 안정화하고 추천은 준비 중으로 표시합니다. 임의 숫자를 실제 평가값으로 제시하지 않습니다.
- **외부 배포·시각적 장식:** 로컬 전체 흐름 검증 뒤 진행합니다. 외부 배포를 오늘 반드시 해야 한다면 마지막 시간에 추가하지 말고 시작 회의에서 B의 별도 작업으로 잡고 기능 범위를 줄입니다.

## 7. 합치기와 완료 판정

각자 `feat/kiosk-ui`, `feat/order-api`, `feat/voice-recommendation`처럼 브랜치를 나눕니다. 공통 계약을 먼저 합치고, 2~3시간째부터 작은 단위로 통합합니다. 하루 끝에 한 번에 합치지 않습니다. B가 통합을 진행하되 기능 오류는 각 담당자가 고칩니다.

완료는 다음 시나리오로 확인합니다.

| 시나리오 | 통과 기준 |
| --- | --- |
| 터치 주문 | 메뉴 → 가능한 온도 → 매장/포장 → 확인 → 실제 DB 저장 → 주문번호 |
| 주문 재전송 | 더블클릭·응답 유실·동시 요청에도 같은 request_id의 주문은 한 건, 같은 번호 |
| 잘못된 주문 | 없는 메뉴·불가능한 옵션·같은 요청 ID의 다른 내용 거부 |
| 실제 음성 메뉴 선택 | 마이크로 말한 등록 메뉴가 선택되고 같은 옵션·확인 단계로 진행 |
| 단계별 음성 | ‘차가운 것’이 온도 단계에서 COLD로, 추천 후보 선택은 현재 후보 안에서 해석 |
| 추천 | 실제 준비된 데이터 기준 최대 4개, 재추천은 조건 재입력, 후보 없음 안내 |
| 음성 실패 | 마이크 권한 거부·빈 음성·처리 실패에서 재시도 또는 터치로 계속 가능 |
| 안내와 상태 | 마이크 누르면 안내 중단, 이전 단계의 늦은 응답이 현재 선택을 덮지 않음 |
| 다음 고객 | 새 주문 시작 시 선택 메뉴·옵션·인식 결과·request_id 초기화 |
| 실행 재현 | 새 DB에서 초기 데이터 입력 후 동일 흐름 동작, 프론트 빌드 성공 |

B는 주문 중복·검증 테스트, C는 해석·추천 계산 테스트를 맡고 A는 전체 사용자 흐름을 확인합니다. 단순히 버튼이 보이는 것을 완료 기준으로 삼지 않습니다.
