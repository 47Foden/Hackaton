# v2: 감각 해석 태그를 사용하는 LLM 직접 추천

상태: 구현·무료 테스트 및 키 소유자의 첫 실제 10회 실험 완료. [실제 결과와 실패 분석](2026-11-09-v2-live/review.ko.md)을 먼저 확인한다. v1보다 실제 추천이 좋아졌다는 결론은 없다. v1 코드·공식 근거 원본·실행 결과는 보존하며, 운영 웹/Whisper는 기존 추천을 계속 사용한다.

현재 기본은 **full/llm**이다. 전체 실제 메뉴를 LLM에 제공하고 LLM이 모호한 표현의 해석·후보 선택·재질문을 직접 판단한다. 서버가 먼저 질문/보류하던 초기 v2 초안은 `--decision-mode guarded`에서만 비교할 수 있다. 기존 추천 경로로 분기하는 혼합 방식은 구현하지 않는다.

공식 페이지/실제 매장 설명을 추가 조사한 [v2 근거 보완 기록](v2-menu-research.md)이 있다. 현재 CLI는 `menu_evidence_researched_v2.json`을 기본 사용하며, 원래 사실/태그 파일은 별도로 보존한다. 프롬프트는 direct-v2.2-researched다. 검색으로 채우지 못한 항목은 미확인으로 유지한다.

## 감각 태그표

`common/experiments/llm_direct/sensory_annotations_v2.json`은 assistant가 기존 공식 설명을 검토해 만든 별도 해석표다. 11개 메뉴/16개 온도 조합에 깔끔함 후보, 묵직함 후보, 단맛, 산미, 탄산, 우유 질감 후보, 떫음, 단맛 잔류를 구분한다. 숫자 맛 점수나 Python 순위 계산은 없다. 요청마다 태그표를 새로 생성하지 않는다.

- `supported`: 공식 설명에 해당 표현이 명시됨. 실측된 감각 강도나 독립 평가 정답이라는 의미가 아님.
- `inferred`: assistant의 해석 가설. 예: 산미·탄산에서 깔끔함을 느낄 가능성. 근거 문장과 추론 이유를 기록하고 출력에도 실측이 아닌 가설이라고 표시.
- `unknown`: 현재 자료로 판단 불가. 없음/false/0으로 바꾸거나 긍정 근거로 인용하면 거부.

깔끔함·묵직함·우유 질감·떫음·단맛 잔류처럼 주관적인 항목은 supported로 격상할 수 없다. 단맛과 끈적한 뒷맛은 다른 축이며 현재 단맛 잔류와 떫음은 모두 미확인이다. 메뉴명만으로 미확인 별칭이나 커피의 감각을 채우지 않는다. 카페인/우유/알레르기는 이 해석표로 추정하지 않고 원래의 확인된 사실을 사용한다.

표의 근거 해시가 메뉴 근거 파일과 다르면 로딩을 거부한다. 자료가 바뀌면 추론도 다시 검토해야 한다. 이 표를 정답으로 삼아 같은 모델의 성능을 평가하는 순환 평가는 하지 않는다. 실제 정답지는 독립된 사람의 관능 평가/사용자 선호 평가 등으로 따로 마련해야 한다.

## 변경한 점

| v1에서 관찰한 문제 | v2 동작 |
|---|---|
| 3000원 예산에 3300원 메뉴 추천 | 원문의 명확한 조건으로 선택 후 서버 재검증. 사전 후보 제한은 eligible 비교 모드에서만 적용 |
| 같은 ID를 HOT/COLD로 중복 | 한 메뉴당 한 후보·한 온도. UNKNOWN_MENU_ID와 DUPLICATE_MENU_ID를 구별 |
| 우유 정보 없음으로 제외 조건 충족 판단 | 온도별 milk 상태가 verified이고 값이 false일 때만 허용. unknown은 false가 아님 |
| 카페인 자료가 있어도 일괄 거부 | 명시적인 0mg 요청은 해당 온도의 확인된 수치와 비교. 수면 영향 요청은 기준 확인 질문 |
| 설명에 없는 사실을 근거로 생성 | 모델은 fit/evidence_ids/matched_tag_ids를 선택. 서버가 사실과 추론을 구분해 짧은 근거 구성 |
| 애매한 표현을 소수 맛 축으로 억지 치환 | 감각 해석표와 원문을 함께 보고 LLM이 후보 또는 구체적인 재질문을 판단 |

LLM은 여전히 사용자 원문과 실제 메뉴/설명을 보고 후보 및 순서를 직접 고른다. 기존 숫자 맛 점수·Pretuning 재정렬은 사용하지 않는다. 조건 추출만 LLM으로 바꾸는 실험도 아니다. 명시적 제한은 서버 보호 장치이며 취향 적합성은 LLM의 선택으로 남는다.

## 정보 흐름과 검증 범위

1. `recommendation_conditions_v2.py`가 원문에서 지원하는 명시적 조건을 읽는다. `CASES.constraints` 같은 사람이 쓴 평가 정답은 읽지 않는다. 해석한 가격의 원문 범위도 기록한다.
2. 기존 공식 근거 파일을 검증하고 메뉴 ID·온도별로 `description`, `milk`, `caffeine_mg` 등의 사실 ID를 부여한다. 미확인은 별도 필드로 남긴다. 가상 설명이나 이름으로 빈 정보를 채우지 않는다.
3. 기본 `full` 모드는 전체 메뉴를 LLM에 보낸다. 선택 후 판매/가격/온도/제외 조건은 서버가 검증한다. `eligible` 모드는 사전 조건 제한의 영향을 살펴보기 위한 별도 비교다.
4. 기본 `llm` 판단 모드에서는 서버가 취향 질문을 먼저 반환하지 않는다. 끈적함·밤 맥락·미확인 자료도 LLM이 직접 평가하고 질문/자료 부족을 반환할 수 있다. `guarded`는 앞선 초안과의 비교용이며 서버 응답은 origin=server_guard로 분리한다.
5. 원문/메뉴/구조화 사실/서버 해석 힌트/감각 해석표를 데이터로 제공한다. 규칙이 찾은 취향 질문 힌트는 강제 질문이 아니다. 숫자 맛 점수는 전송하지 않는다. 사용자·메뉴·해석표의 지시는 데이터로 구분하며 모델 수준 주입 방어가 완전하다고 주장하지 않는다.
6. ID·온도·중복·사실과 태그의 소유 메뉴/온도를 검사한다. sweet/refreshing fit에는 해당 태그 및 그 근거 설명 ID가 필요하다. 추론 태그는 근거 사실을 함께 인용해야 하며 unknown 태그 인용은 거부한다. 우유 미포함 fit에는 명시적 false 사실이 필요하다.
7. 근거는 검증된 가격·온도·인용한 설명과 별도 표시한 추론으로 구성한다. 후보 순서는 보존한다. LLM 질문은 한 번에 최대 하나이며, 그 의미 적합성은 사람 검토가 필요하다. 이전 답변을 유지하는 대화 세션 처리는 아직 별도 구현이 필요하다.

동적 enum과 JSON Schema 구조화 출력은 [공식 OpenAI 문서](https://developers.openai.com/api/docs/guides/structured-outputs)를 기준으로 작성했다. 첫 실제 실험에서는 API가 요청을 수용했으나 응답 의미·식별자 검증에서 다수 실패했다. API 형식 수용과 추천 품질은 별개다.

## 조건 해석의 제한

- 지원: 숫자/쉼표 금액, 일부 한글 금액(삼천·삼천오백), 일부 혼합 금액(3천·1만), 이하/미만/이상/초과/까지/한 장. 차가운/차갑/아이스 등과 따뜻/뜨거운 등, 명시적 커피 제외·우유 제외·카페인 0 요청.
- 질문: 금액 조건 미지정/부정/충돌, 소수 금액, 지원하지 않는 한글 조합, 온도 부정/충돌, 디카페인·카페인 적게의 기준, 끈적함·뒷맛 자료 부재, 밤/수면 영향, 알레르기 안전성.
- 한계: 한국어 전체를 해석하지 않는다. 말 바꾸기·인용문·복합 부정·규칙 밖 표현을 놓치거나 불필요하게 질문할 수 있다. 원문도 LLM이 평가하므로 서버 해석이 원문 전체의 정답이라는 보장은 없다. 필요하면 사용자가 조건을 명시적으로 확인하는 UI를 별도로 실험해야 한다.
- 카페인 0mg은 공식 표기량 기준이다. 실제 수면 영향이나 건강/알레르기 안전성을 보장하지 않는다. 현재 milk=false인 실제 근거가 없으므로 우유 제외 후보가 없다는 결과는 제품에 우유가 모두 들어 있다는 의미가 아니다.
- 근거 ID가 맞다는 것과 사용자의 취향에 적합하다는 것은 다르다. fit 분류와 질문의 의미 적합성은 사람이 평가해야 한다. 질문 문장은 자유 텍스트이므로 질문 자체의 사실 오류도 검토 대상이다.

## 무료 재현

저장소 루트 PowerShell, Python 3.11 이상:

```powershell
$env:PYTHONPATH = (Resolve-Path backend).Path
python -B -m unittest discover -s backend/tests -p test_llm_direct_v2.py -v
python -B -m unittest discover -s backend/tests -p test_sensory_tags.py -v
python -B -m app.experiments.compare_recommendations_v2 --v1-report docs/experiments/2026-11-09-first-live/results.json --mode mock --repeat 2 --output-dir work/v2-mock
```

v1의 실제 DB 스냅샷을 재사용해 입력 차이를 줄인다. 현재 메뉴와 다를 수 있으므로 새로운 실제 메뉴 비교는 `/api/menus` JSON을 `--menus`로 제공한다. 기본 mock은 고정 자료 부족 응답이며 다섯 발화 모두 model transport로 전달된다. origin=mock_fixture, 실제 api_calls=0, transport_calls는 fixture 호출 횟수다. 이 고정 응답을 실제 모델 성능으로 제시하지 않는다. guarded 서버 응답은 별도 origin이다. 사람 평가란은 null이다.

결과는 `results.json`과 `results.ko.md`이며 모델 요청 수·응답 주체·조건 해석·제외 사유·사실 ID·근거·usage·비용·정보 차이를 기록한다. 기존 경로는 원래 함수 반환/오류를 기록하며 v2 통과율과 같은 기준의 정확도로 비교하면 안 된다.

## 이후 유료 실험 (이번 작업에서는 실행하지 않음)

키 소유자가 직접 위 비교 명령의 mode를 live로 바꾸고 `--allow-paid-api --env-file backend/.env --model <선택한 모델>`을 지정해야 한다. 단가는 확인 후 `--rates INPUT CACHED_INPUT OUTPUT`으로 넣는다. 키 파일은 live에서만 읽는다. API 접근 오류/추가 재시도는 자동으로 처리하지 않는다. 결과 폴더에 이미 결과가 있으면 중단해 v1/v2 결과를 덮어쓰지 않는다.

`--max-api-calls`는 기본 10회이며 발화 수×반복이 상한을 넘으면 키 파일 접근 전에 중단한다. 이는 호출 횟수 제한이지 결제 금액의 강제 상한이 아니다. live에서는 api-attempts.json에 각 시도 시작과 응답/usage를 순차 기록한다. 중단돼도 그 파일을 먼저 확인하며 같은 폴더의 재실행은 거부한다. 이 파일에도 요청 프롬프트/인증 헤더/키를 저장하지 않는다. GPT-5.4 mini 계열은 reasoning none을 명시한다. 재시도는 없다.

후보 제한 전후 비교 시 모델·메뉴·사실·발화·반복 횟수는 맞추고 candidate-mode만 바꾼다. 원래 v1과 비교할 때는 정형 사실·조건 보호 장치·서버 질문·근거 생성 방식이 모두 바뀐 시스템 비교임을 명시한다. API 호출을 건너뛴 서버 응답을 모델 개선으로 세거나 mock 통과율을 실제 성능으로 제시하지 않는다. 추가 검증/재요청 기능은 비용 및 최초 실패율을 따로 기록하도록 후속 버전에서 검토한다.
