# 추천 구조 변경 제안 — 문장 해석과 후보 선택을 LLM에 맡기기

> **제안 요지:** 사용자 표현을 Python이 먼저 확정해 후보를 막는 구조에서, **LLM이 원문을 해석하고 메뉴를 직접 선택한 뒤 서버가 사실을 검증하는 구조**로 실험을 진행하고자 합니다. 확인된 일부 표현에서 사전 규칙의 오해가 추천을 막는 문제를 재현했습니다. 전체 정확도 개선이나 즉시 main 교체를 주장하는 제안은 아닙니다.

확인 기준: 2026-11-12 원격 main `f6bbfcb` / 실험 브랜치 `experiment/taejun-llm-semantic-direct`.

## 1. 현재 main의 한계

현재도 LLM은 사용자 원문을 읽고 후보를 직접 선택합니다. 다만 그 전에 Python이 맛·제외·가격·온도 등을 해석해 **허용 후보와 응답 범위**를 정합니다. 앞단이 문장을 잘못 읽으면 LLM이 원문을 이해하더라도 적합 후보를 선택할 수 없습니다.

**같은 실제 메뉴 45개로 현재 main을 무료 재현한 예시**

| 사용자 발화 | 의도 | main의 Python 해석 및 영향 |
|---|---|---|
| 레몬 말고 딸기 | 레몬 제외, 딸기 선호 | 딸기와 레몬을 모두 선호로 분류 → 허용 후보 0개 |
| 레몬이랑 망고는 빼고 딸기 | 레몬·망고 제외, 딸기 선호 | 세 맛을 모두 선호로 분류 → 허용 후보 0개 |
| 레몬은 싫지 않아요 | 레몬을 금지하지 않음 | 레몬 선호로 분류 → 레몬 메뉴 3개로 후보 제한 |

특히 앞의 두 사례는 응답 스키마의 추천 배열 상한도 0이 됩니다. 단순히 프롬프트에 “문장을 잘 이해하라”고 덧붙여 해결할 수 없는 사전 제한입니다. 여러 대상을 묶어 제외하거나 부정·정정하는 표현을 규칙으로 계속 보완하면 유사한 예외 처리가 늘어날 수 있습니다.

## 2. 무엇을 바꾸는가

| 구분 | 현재 main | 제안하는 실험 구조 |
|---|---|---|
| 자연어 해석 | Python 규칙과 LLM이 함께 수행 | **LLM이 원문 전체를 해석** |
| 후보 선택 | Python이 허용한 범위 안에서 LLM 선택 | **실제 메뉴 자료를 보고 LLM이 직접 선택** |
| Python 역할 | 의미 해석·사전 후보 제한·응답 검증 | **선택 뒤 확인 가능한 사실·계약 검증** |
| 유지하는 검사 | 메뉴 ID·판매 여부·가격·온도·자료 등 | 동일하게 유지. 옵션 합산 가격 및 해석 결과와의 충돌도 검사 |
| 호출 수 | 추천 요청 1회 | 해석과 선택을 같은 응답으로 받아 **1회 유지** |
| 맛 점수표 | 현재 직접 추천에서는 숫자표 사용 안 함 | 숫자표 없이 진행. Python 점수로 재정렬하지 않음 |

**현재:** 원문 → Python 해석·후보 제한 → LLM 선택 → 서버 검증
**실험:** 원문 + 확인된 메뉴 자료 → LLM 해석·선택 → 서버 사실 검증

“규칙을 모두 없애자”는 제안이 아닙니다. **자유로운 문장의 의미 판단과, 실제 메뉴의 사실 검증을 분리하자**는 제안입니다. 검증할 예산·제외 조건 자체를 LLM이 잘못 해석하거나 누락할 수 있다는 위험은 남습니다.

## 3. 지금까지 확인한 근거

| 구분 | 확인한 내용 | 해석 범위 |
|---|---|---|
| 현재 main 무료 확인 | 위 세 발화의 잘못된 조건·후보 제한 재현 | 현재 main 코드의 구조적 원인 확인. 실제 LLM 호출 아님 |
| 실제 유료 비교 | 복합 제외에서 기존 비교 방식은 후보 0개, 새 의미 해석 방식은 두 제외 조건을 반환하고 딸기 후보 5개 추천 | 실제 응답에서 가능성 확인. 각 발화 1회 |
| 실제 유료 비교의 한계 | 새 방식의 일반 딸기 요청은 중복 ID, 이중 부정은 추천+미해결 상태 모순으로 거부 | 새 방식이 전반적으로 더 좋다는 결론은 아직 불가 |
| v2 무료 보완 | 동일 중복은 사실 검증 뒤 제거·기록. 추천/자료 부족 형식을 분리. 허용 표현 지침 강화 | 중복 실패 응답의 5개 후보 전달을 실제 과거 응답 재생으로 확인 |
| 회귀 검증 | 무료 테스트 76개 통과 | 코드·계약·사실 검사 근거. 실제 모델 정확도 수치 아님 |
| 이후 실제 main 대 v2 비교 | 새로운 말투 4개 각 1회에서 전달 가능 응답 main 2/4, v2 4/4. 단순·복합 제외는 v2가 각각 딸기 후보 5개 전달 | v2도 이중 부정 해석 오류·선호 기록 누락·중복 생성은 남음. 4/4 전달이 정확도 100%는 아님 |

**비교 기준 주의:** 첫 8회 유료 비교의 기존 코드는 `769d2d9` 기반이었습니다. 이후 별도 8회에서는 실제 main `f6bbfcb` 원본과 의미 해석 v2를 새 말투로 비교했습니다. 두 실험의 표본을 같은 조건인 것처럼 합치지 않습니다. 최신 비교에서 v2의 구조화된 해석은 사전 기준과 2/4 일치했고, 원응답 계약 통과는 3/4이며 나머지 중복 1건은 서버가 검증 후 정규화했습니다. 이 v1/v2는 과거 추천 실험 V1~V3와 다른 버전 표기입니다.

## 4. 기대 효과와 남은 검증

**기대 효과:** 확인한 사례처럼 사전 규칙의 오해로 적합 후보가 사라지는 문제를 줄이고, 나열된 제외·부정·말 바꾸기 등 문맥 판단을 LLM이 수행할 수 있게 합니다. 실제 원문과 해석·선택 결과를 함께 기록해 원인 분석도 가능하게 합니다.

**남은 위험:** LLM 자체의 오해·조건 누락, 불필요한 자료 부족 판단, 응답 규격 오류는 계속 평가해야 합니다. 메뉴 설명에 특정 맛 단어가 없다는 것은 원재료 미포함·알레르기 안전 보장이 아닙니다. 실제 DB/STT/운영 배포도 별도 검증 대상입니다.

**시간·비용:** 최신 main 대 v2 8회 비용 합계는 약 $0.195였습니다. 평균 API 시간은 main 약 2.48초, v2 약 3.66초로 이번에는 신규가 더 걸렸습니다. 비용은 양쪽 약 $0.098/$0.097로 비슷했고 양쪽 캐시 입력은 0토큰이었습니다. 작은 표본이며 속도/비용 개선을 입증하지 않습니다. 이번 제안의 주목적은 문맥 처리와 사전 제한 오류 개선입니다.

## 5. 팀에 요청하는 결정

1. 현재 main을 바로 대체하기보다 **별도 실험 브랜치에서 이 역할 분리를 검증**하는 방향을 검토 부탁드립니다.
2. 최초 main 대 v2 비교는 완료했습니다. main 교체 판단 전에는 이중 부정·조건 누락을 보완하고 가격·온도·자료 부족·반복 실행 등으로 검증을 넓혀야 합니다. 원응답 오류와 정규화 후 전달 가능 여부를 계속 구분합니다.
3. 추가 유료 비교가 필요하면 별도 범위·비용 확인 후 키 소유자가 실행합니다. 이번 문서 갱신은 저장된 결과만 사용했으며 새 유료 호출은 하지 않았습니다. [최신 실제 비교 검토](main-v2-live-results.ko.md)를 함께 확인해 주세요.

기존 main·공유 브랜치·웹/음성 기본 경로·DB·공용 Docker 설정은 변경하지 않았습니다. 실험 수정은 별도 브랜치로 공유하며 main 병합은 별도 검토합니다.
