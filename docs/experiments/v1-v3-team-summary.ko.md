# 팀 공유: LLM 직접 추천 v1~v3 개발 과정

## 먼저, 모델을 재학습한 것은 아닙니다

v1~v3는 **같은 사전 학습 모델에 제공하는 자료·프롬프트·응답 형식·서버 검증을 바꿔 가며 실제 결과를 확인한 실험 버전**입니다. 이 프로젝트에서 모델 가중치를 학습하거나 파인튜닝하지 않았습니다. 실패 결과를 읽고 사람이 코드를 수정했으며, 이전 실험 응답을 모델이 자동으로 기억하고 다음 요청에서 학습한 구조도 아닙니다.

실제 소규모 실험은 `gpt-5.4-mini-2026-03-17`을 사용했습니다. 데이터셋의 예상 메뉴는 평가용이고 LLM 요청에 넣지 않았습니다. API 요청 시 실제 메뉴·가격·가능 온도·판매 여부와 확인된 메뉴 사실을 제공합니다.

팀원이 ‘어떻게 학습했나요?’라고 물으면 이렇게 설명할 수 있습니다.

> 모델을 별도로 학습시킨 것은 아닙니다. v1에서 직접 추천을 분리 구현하고, 실제 실패를 보고 v2에서 사실 자료와 검증을 보강했습니다. v2는 출력 계약이 복잡해 오류가 많아, v3에서는 단일 후보와 짧은 근거 필드로 단순화했습니다. 이후 쉬운 발화와 말투 변경 실험으로 동작을 확인했습니다.

## 기존 방식과 직접 추천의 차이

| 항목 | 기존 방식 | LLM 직접 추천 |
|---|---|---|
| 메뉴 맛 자료 | LLM으로 미리 만든 숫자 점수 CSV 사용 | v3 모델 입력에는 숫자 맛 점수 사용 안 함 |
| 사용자 문장 처리 | Python의 제한된 규칙·정규식 | LLM이 원문과 메뉴 자료를 함께 평가 |
| 최종 후보 선택 | Python의 점수 계산·순위 | LLM이 실제 메뉴 ID와 온도를 직접 선택 |
| 서버 역할 | 원래 추천 로직 실행 | 선택 결과의 ID·판매·가격·온도·확인 가능한 제외 조건·근거 검증 |
| 불확실한 상황 | 기존 규칙 동작 | 질문 또는 자료 부족 응답 가능 |

기존 방식이 요청마다 LLM으로 맛 점수표를 만드는 구조라는 뜻은 아닙니다. 기존 CSV는 사전에 생성한 자료입니다. 새 방식도 매 요청마다 그 CSV를 다시 만들지 않습니다. LLM이 고른 후보를 기존 맛 점수로 다시 정렬하지 않습니다.

## 버전별 변경 과정

### v1 — 직접 추천이 가능한지 분리해서 확인

- 기존 추천·웹·Whisper와 분리한 텍스트 실험 모듈을 만들었습니다.
- LLM이 원문과 실제 메뉴 자료를 보고 메뉴 후보 ID·근거·질문 등을 구조화해 반환하도록 했습니다.
- 키 없이 요청 구성·검증·오류 처리를 시험할 수 있게 transport를 교체 가능한 구조로 만들었습니다.
- 실제 응답에서 예산 위반, 중복 메뉴 ID, 미확인 제외 조건 처리 문제가 관찰됐습니다.
- 연결 확인 1회와 기본 발화 5개를 각 1회 실행했습니다. 기본 5개 중 서버 검증 통과는 1개였으며 추천 정확도 20%라는 의미는 아닙니다.

### v2 — 메뉴 근거·미확인 상태·서버 검증 보강

- 온도별 설명·우유·카페인·알레르기 자료를 출처/확인일과 함께 구분했습니다. 미확인을 false·0·없음으로 바꾸지 않았습니다.
- 설명 자료를 추가 조사하고, 사실과 assistant의 감각 추론 태그를 분리했습니다. 이 태그는 독립된 정답지나 실측 맛 자료가 아닙니다.
- LLM은 후보·온도·fit·태그 ID·근거 ID를 반환하고 서버는 해당 메뉴/온도의 근거인지 검사했습니다.
- 기본 full/llm 모드에서 전체 메뉴를 보고 LLM이 후보 선택과 질문 여부를 판단했습니다. 기존 방식으로 자동 분기하는 혼합 추천을 기본으로 삼지 않았습니다.
- 새 개발 발화 10개 실제 실행에서 검증 통과는 2개(추천 1개·질문 1개), 거부는 8개였습니다.
- 실패 원인은 긴 태그 ID 복사/범위 오류, milk/caffeine이라는 fit 단어의 의미 혼동, 우유 미포함을 확인하지 않고 후보를 고른 문제 등이었습니다.

기능과 검증을 늘리는 것이 실제 성공률을 자동으로 높이지 않았습니다. 출력 요구가 복잡해 정상 후보도 거부되는 설계 부담이 생겼다는 점을 배웠습니다.

### v3 — 후보와 근거 계약을 단순화

- 후보를 최대 1개로 줄이고 `fit`과 긴 태그 ID를 제거했습니다.
- 모델 입력에서 감각 추론 태그표를 제외하고 실제 확인된 사실 값을 간결하게 제공했습니다. 출처와 자료 상태는 서버에 보존합니다.
- 모델은 짧은 `basis_fields`를 선택하고 서버가 해당 메뉴·온도의 사실에 연결해 근거를 구성합니다.
- 응답은 `recommend`, `clarify`, `insufficient_data`로 구분합니다. 미해결 요구와 특정 요청 상품명도 기록합니다.
- 미등록 상품의 임의 대체와, 미해결 요구가 남은 추천을 검증합니다. 단, 모델이 그 요구 자체를 누락하는 문제까지 해결한 것은 아닙니다.
- 가격·온도·판매·우유·카페인 등 사실 검증을 유지하며 LLM 선택을 기존 숫자 점수로 보정하지 않습니다.

## 실제 실험 결과

| 실험 | 실행 범위 | 관찰 결과 | 비용 추정 | 평균 지연 |
|---|---|---|---:|---:|
| v1 | 연결 1회 + 기본 발화 5회 | 기본 발화의 서버 검증 통과 1/5 | $0.02487450 | 여기서는 직접 비교하지 않음 |
| v2 | 새 개발 발화 10개 각 1회 | 서버 통과 2/10: 추천 1·질문 1 | $0.11519400 | 2.656초 |
| v3 쉬운 발화 | 5개 각 1회 | 사전 메뉴·조건·근거 기준 5/5 충족 | $0.01153200 | 2.263초 |
| v3 후속 | 원문 재실행 5 + 말투 변경 5 | 원문 5/5, 변경 4/5가 사전 기준 충족 | $0.01458600 | 1.879초 |

v1/v2의 ‘서버 검증 통과’와 v3의 ‘사전 기준 충족’은 같은 지표가 아닙니다. 발화 난도·제공 정보·응답 계약이 달라 20%→20%→100%처럼 정확도 상승 그래프로 제시하면 안 됩니다. mock/단위 테스트 통과도 추천 성능이 아닙니다.

### v3에서 확인한 점

- 쉬운 설명 대응: 레몬 산미·탄산→레몬에이드, 딸기·우유→딸기라떼, 청포도·탄산→청포도에이드를 선택했습니다.
- 원문 재실행 5쌍 중 메뉴·온도·행동은 4쌍 동일했습니다. 카페라떼→에스프레소 변화는 둘 다 허용된 따뜻한 커피여서 오답은 아닙니다.
- 말투 변경 5쌍 중 4쌍은 같은 후보를 선택했습니다. 나머지는 ‘커피 종류 제외’에서 카페인까지 제외할지 불필요하게 질문했습니다.
- 조건을 만족하는 메뉴를 고를 가능성을 확인했지만, 질문의 과잉·근거 필드 변화·반응속도 문제는 남아 있습니다.

## 현재 서비스 연결 상태

기존 녹음 경로는 다음과 같습니다.

`녹음 → /api/voice/interpret → Whisper 텍스트 → 주문 해석 → 필요한 경우 기존 recommendation.recommend → 화면`

v3를 채택했다는 팀 의사결정만으로 이 경로가 자동 변경되지는 않습니다. 현재 코드의 녹음 경로는 기존 추천을 호출합니다. v3 실험은 별도 CLI로 실행해 왔습니다.

이번에 개발용 녹음 화면에 텍스트 시험란과 `/api/experiments/recommend-text` API를 추가했습니다.

- 기본은 기존 방식입니다. LLM v3는 서버 설정을 켜고 사용자가 유료 API 버튼을 선택할 때만 실행합니다.
- 텍스트를 직접 넣어 Whisper 이후에 사용할 추천 함수의 후보·근거·질문·자료 부족·시간·usage를 확인합니다.
- 텍스트 시험은 실제 음성 인식, 음성 주문 전체 분기, 질문 후 대화 상태를 검증하지 않습니다.
- 키는 서버 환경에서만 사용합니다. 브라우저에 키를 입력하거나 코드에 넣지 않습니다.
- 텍스트 시험 UI는 Vite 개발 모드에만 표시하며 기존 녹음·주문 기본 경로는 바꾸지 않습니다.

이 도구 환경에서는 기존 localhost 서비스와 Docker 엔진에 접근하지 못했으므로 현재 실행 중인 실제 컨테이너에 반영됐다고 단정하지 않습니다. 로컬 실행 후 설정 상태와 응답의 `engine`을 확인해야 합니다. 배포 서버에 v3가 연결되었다는 의미도 아닙니다.

## 남은 작업과 한계

1. 실제 음성 경로를 v3에 연결하는 별도 설정과 정책이 필요합니다. 현재는 텍스트 시험에서만 선택할 수 있습니다.
2. 재질문 뒤의 답변을 기존 요구와 합쳐 재추천하는 대화 상태 처리는 아직 없습니다.
3. 독립적인 취향 평가와 새 발화 데이터셋이 필요합니다. 설명에서 만든 기대 메뉴만으로 실제 만족도를 입증하지 않습니다.
4. 모델의 조건 누락, 복잡한 한국어 부정, 미확인 성분·뒷맛, 주입 방어는 완전히 해결되지 않았습니다.
5. LLM 경로는 기존 ms 수준 코드보다 느리고 유료 호출이 필요합니다. 캐시로 낮아진 비용이 항상 재현된다고 보장하지 않습니다.
6. 가격·판매 상태·레시피 자료의 최신성 확인과 주문 시점 재검증이 중요합니다.

GitHub에는 사용자가 v2 커밋 `b2c8f77`까지 push한 기록이 있습니다. 이번 v3·텍스트 시험 변경은 별도로 commit/push하지 않았으므로 팀원의 checkout에 자동 반영되지는 않습니다.
