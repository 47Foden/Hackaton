# 시스템 아키텍처

이 문서는 **화면, 서버, 음성 인식 모델, DB가 어떤 역할을 맡고 어떻게 연결되는지** 설명합니다. 프로젝트의 목적과 기능 범위는 [프로젝트 개요](./project-overview.md)를 기준으로 합니다.

문서에서 사용하는 상태는 다음과 같습니다.

- **현재 구현:** 저장소의 코드와 설정으로 동작하는 부분입니다.
- **구현 예정:** 개요의 기능을 만들기 위한 구조와 처리 방향입니다. 아직 완성된 기능이 아닙니다.
- **미정:** 팀이 결정하거나 실제로 검증해야 하는 부분입니다.

## 1. 전체 구조부터 이해하기

사용자는 키오스크의 브라우저 화면을 조작합니다. 화면은 서버에 필요한 처리를 요청하고, 서버는 음성을 글자로 바꾸거나 메뉴를 찾고 주문을 기록한 뒤 결과를 화면에 돌려줍니다.

```text
사용자: 터치 또는 말하기
          ↕
프론트: 화면 표시 · 녹음 · 음성 안내 재생
React + TypeScript
          ↕ 요청과 결과
백엔드: 입력 해석 · 메뉴 추천 · 옵션 확인 · 주문 처리
Python + FastAPI
          ├── Whisper: 음성을 텍스트로 변환
          ├── 메뉴 속성표: 추천 계산에 사용
          └── PostgreSQL: 메뉴·옵션·주문 데이터 관리
              주문 기록의 유일한 원본
```

위 그림은 **목표로 하는 논리 구조**입니다. 각 상자가 반드시 별도의 서버나 컨테이너라는 뜻은 아닙니다. 특히 Whisper를 백엔드와 같은 실행 환경에 둘지, 별도 GPU 서버에서 실행할지는 아직 결정하지 않았습니다.

## 2. 구성 요소별 역할

| 구성 요소 | 담당하는 일 | 담당하지 않는 일 |
| --- | --- | --- |
| 프론트 — React + TypeScript | 화면 표시, 터치 입력, 마이크 입력, 안내 재생, 현재 주문 단계와 선택 내용 표시 | DB 직접 접속, Whisper 추가 학습 |
| 개발 도구 — Vite | 개발 중 화면 실행, 변경 사항 반영, 배포용 화면 파일 생성 | 주문 처리, 음성 인식 |
| 백엔드 — Python + FastAPI | 프론트 요청 수신, 음성 처리 연결, 메뉴·옵션 검증, 추천 및 주문 처리 | 화면을 직접 조작하는 일 |
| Whisper | 음성을 텍스트로 변환 | 메뉴 추천, 가격 결정, 주문 저장 |
| 추천 로직과 메뉴 속성표 | 사용자의 취향·조건을 실제 메뉴와 비교하여 후보 선택 | 음성을 글자로 바꾸는 일 |
| PostgreSQL | 메뉴·옵션 등 관계가 있는 데이터를 저장하는 기반 | 화면 표시, 모델 실행 |

**FastAPI는 학습 도구가 아닙니다.** 학습 완료된 모델을 주문 서비스에서 사용할 수 있도록 연결하는 서버의 역할입니다.

메뉴 조회, 음성 처리, 추천, 주문 처리는 우선 **하나의 백엔드 안에서 책임을 나누는 방향**으로 설계합니다. 처음부터 기능마다 서버를 나누는 구성을 전제하지 않습니다.

## 3. 현재 실제로 실행되는 구조

현재 Docker Compose에는 아래 세 서비스가 있습니다.

| 서비스 이름 | 실행 내용 | 접속 방법 |
| --- | --- | --- |
| `frontend` | Vite 개발 서버와 React 화면 | 브라우저에서 `http://localhost:5173` |
| `backend` | FastAPI 서버 | 브라우저에서 `http://localhost:8000/docs` |
| `db` | PostgreSQL | 백엔드에서 `db:5432`로 접속 |

현재 연결 확인 요청은 다음 경로로 이동합니다.

```text
브라우저가 http://localhost:5173을 엽니다.
  → Vite가 React 화면을 제공합니다.
  → 화면이 /api/health를 요청합니다.
  → Vite가 요청을 backend:8000으로 전달합니다.
  → FastAPI가 PostgreSQL에 SELECT 1을 실행합니다.
  → 연결 결과가 화면으로 돌아옵니다.
```

`/api/health`는 시스템이 연결되어 있는지 확인하는 주소입니다. 현재 성공하면 `{"status":"ok","database":"connected"}`를 반환하고, DB 연결 오류는 503 응답으로 알립니다.

여기서 **프록시**는 요청을 다른 서버로 전달해 주는 기능입니다. 현재는 Vite가 `/api`로 시작하는 요청을 백엔드로 전달합니다.

### 주소가 서로 다른 이유

- 브라우저에서 `localhost`는 사용자의 컴퓨터를 가리킵니다.
- 컨테이너 안에서 `localhost`는 그 컨테이너 자신을 가리킵니다.
- 컨테이너끼리는 Compose의 서비스 이름인 `backend`, `db`로 찾습니다.
- 따라서 프론트 화면 코드에 `http://backend:8000`을 직접 넣어 브라우저가 호출하도록 하지 않습니다. 현재 화면은 `/api`를 요청하고 Vite가 전달합니다.

현재 메뉴·주문 테이블, 메뉴 API, 추천 로직, 음성 인식 연결은 아직 구현하지 않았습니다. 연결 확인 성공이 서비스 기능 완성을 뜻하지는 않습니다.

## 4. 사용자의 입력이 주문이 되는 과정 — 구현 예정

### 4.1 화면 시작과 메뉴판

1. 프론트가 로고와 주문하기 버튼을 보여줍니다.
2. 사용자가 버튼을 누르면 기본 주문 화면으로 이동합니다.
3. 프론트가 백엔드에 메뉴 데이터를 요청합니다.
4. 백엔드는 메뉴 데이터를 읽어 화면에 돌려줍니다.
5. 프론트가 안내, 간소화된 메뉴판, 전체 메뉴판 보기 버튼, 마이크 버튼을 표시합니다.

메뉴판 확대와 표시 위치는 프론트의 책임입니다. 메뉴 ID, 이름, 가격, 제공 가능한 옵션 등의 기준 데이터는 백엔드가 관리합니다. 구체적인 저장 테이블은 DB 설계에서 정합니다.

### 4.2 터치 주문

```text
메뉴 터치
  → HOT/COLD 선택
  → 매장/포장 선택
  → 최종 주문 내용 확인 및 ‘주문 확정’ 버튼 입력
  → 공통 주문 데이터 구성 및 전송
  → 백엔드가 메뉴와 옵션 확인
  → 주문 기록 저장 및 주문번호 발급
  → 화면에 주문번호 표시
```

프론트는 사용자가 무엇을 선택했는지 관리하고, 백엔드는 선택한 메뉴가 실제로 존재하는지와 옵션이 유효한지 최종 확인합니다. 가격을 사용하는 경우에도 화면에서 전달된 가격을 그대로 신뢰하지 않고 기준 데이터로 확인하는 방향입니다.

터치·음성 모두 최종 주문 내용을 화면에서 확인하고 **‘주문 확정’ 버튼을 누른 뒤** 저장을 요청합니다. 메뉴를 누르거나 음성으로 메뉴를 선택한 순간 곧바로 저장하지 않습니다. 확인 화면의 세부 배치는 UI 설계에서 정합니다.

### 4.3 음성 입력

1. 사용자가 마이크 버튼을 누릅니다.
2. 프론트가 현재 재생 중인 안내를 멈춥니다.
3. 프론트가 마이크 권한을 확인하고 음성을 녹음합니다.
4. 녹음이 끝나면 음성 데이터를 백엔드에 전달합니다.
5. 백엔드가 파일을 확인하고 모델이 읽을 수 있도록 전처리합니다.
6. Whisper가 음성을 텍스트로 변환합니다.
7. 백엔드의 해석 로직이 텍스트와 현재 주문 단계를 보고 다음 행동을 정합니다.
8. 프론트가 그 결과에 따라 메뉴 선택, 추천 결과, 재입력 안내 등을 표시합니다.

예를 들어 ‘차가운 걸로’는 처음 주문 화면에서는 추천 조건이 될 수 있고, 온도 선택 화면에서는 COLD 옵션 선택이 될 수 있습니다. 따라서 **인식한 문장뿐 아니라 현재 주문 단계도 해석에 필요**합니다. 단계 정보를 요청에 담을지 서버에서 관리할지는 API 설계에서 정합니다.

음성 파일은 JSON 문장과 같은 것이 아닙니다. 파일 전송 방법과 별도로 보낼 단계 정보의 형식은 API 명세에서 정의합니다.

#### MP3와 녹음 종료 방식

- 팀이 제시한 입력 파일 형식은 MP3입니다.
- 브라우저에서 녹음한 결과가 항상 MP3라고 가정하지 않습니다.
- 녹음 형식, MP3 변환 여부·위치, 모델 입력 전처리는 구현 시 결정합니다. 파일 확장자만 바꾸는 방식은 변환이 아닙니다.
- 녹음을 버튼으로 끝낼지, 무음을 감지해 끝낼지, 시간 제한을 둘지는 미정입니다.
- 상시 청취나 말하는 도중 계속 결과를 표시하는 실시간 스트리밍은 현재 확정 범위가 아닙니다.

### 4.4 음성 텍스트 해석

| 해석 결과 | 다음 행동 |
| --- | --- |
| 등록 메뉴를 식별할 수 있음 | 메뉴를 선택하고 옵션 단계로 이동 |
| 취향이나 조건을 설명함 | 추천 로직 실행 |
| 현재 단계의 옵션을 선택함 | 해당 옵션을 반영하고 다음 단계 안내 |
| 인식 또는 의미 해석이 어려움 | 재입력 안내 |

메뉴명 일치 판정과 별칭 처리, 취향 표현 추출에 규칙을 쓸지 별도의 모델을 쓸지는 미정입니다. Whisper가 이 판단까지 모두 담당한다고 가정하지 않습니다.

## 5. 추천은 어떻게 구성하나요? — 구현 예정

추천에는 **사전 준비 과정**과 **실제 주문 중 계산 과정**이 있습니다.

### 사전 준비

메뉴마다 음료 종류, 카페인, 단맛, 쓴맛, 신맛, 가격 등의 정보를 준비합니다. 메뉴가 행, 속성이 열인 표를 생각하면 됩니다.

팀은 모델을 여러 번 실행한 결과의 평균으로 속성 점수를 만드는 방식을 검토하고 있습니다. 사용할 모델, 반복 횟수, 점수 범위와 계산법은 미정입니다. 이것은 Whisper의 추가 학습과 별개의 작업입니다.

가격과 제공 옵션처럼 실제 메뉴 정보로 확인 가능한 값은 메뉴 기준 데이터와 일치해야 합니다. 음료 종류 같은 분류 값과 단맛 점수 같은 수치를 같은 방식으로 평균 내도록 가정하지 않습니다.

### 주문 중 추천

```text
‘차갑고 달달한 티 종류 아무거나’
  → 음성 인식으로 텍스트 확보
  → 차 종류 · 차가운 음료 · 단맛 선호 등의 조건 해석
  → 실제 제공 가능한 메뉴와 조건 비교
  → 메뉴 속성표를 이용해 후보 평가
  → 최대 4개 표시를 기본 방향으로 결과 반환
  → 사용자가 사진 또는 음성으로 선택
```

사용자의 긍정·부정 조건을 어떤 점수로 계산할지는 미정입니다. 원안의 `Max 4 / MIN 4`만으로 최종 알고리즘을 확정하지 않습니다. 조건에 맞는 메뉴가 없는 경우도 별도로 처리해야 합니다.

재추천 버튼을 누르면 프론트는 음성 입력 단계로 돌아갑니다. 새로운 입력을 받아 추천을 다시 요청하며, 이전 추천 응답이 늦게 도착해 새 화면을 덮어쓰지 않도록 처리하는 것이 설계 방향입니다.

## 6. 주문 데이터와 저장의 책임 — 구현 예정

터치와 음성은 입력 방법만 다르고, **최종 주문 처리 경로는 하나로 합칩니다.** 두 방식에 별도의 주문 저장 로직을 만들지 않는 방향입니다.

```text
터치로 선택 ─┐
             ├→ 최종 확인 → 공통 주문 데이터 → 검증 → PostgreSQL 저장 → 주문번호 응답
음성으로 선택 ┘
```

JSON은 데이터를 주고받는 표현 형식입니다. 별도의 `.json` 파일로 주문을 저장하는 것이 아닙니다. **PostgreSQL을 주문 기록의 유일한 원본으로 사용합니다.** CSV 저장·내보내기는 MVP에 포함하지 않으며, 추후 필요할 때 DB에 저장된 주문을 내보내는 기능으로 추가합니다.

| 데이터 | 처리 방향 | 확정 여부 |
| --- | --- | --- |
| 메뉴·옵션 등 기준 데이터 | PostgreSQL을 활용하는 방향 | DB 기술 확정, 테이블 설계 예정 |
| 현재 선택한 메뉴와 단계 | 프론트가 화면에 필요한 상태 유지 | 서버와 공유하는 방식 미정 |
| 최종 주문 | 공통 JSON으로 전달하고 PostgreSQL에 저장 | 저장 방식 확정, 필드·테이블 설계 예정 |
| 주문 CSV | 추후 필요할 때 DB에서 내보내기 | MVP 범위에서 제외 |
| 추천 속성표 | 사전 생성 후 추천 시 사용 | 파일 또는 DB 등 보관 방식 미정 |
| 음성 원본·학습 모델 | 보관이 필요한 경우 별도 파일 저장 환경 사용 | 저장 위치·보관 기간 미정 |

주문 저장 규칙은 다음과 같이 확정합니다. **확정된 설계이며 실제 구현은 예정 상태**입니다.

1. 백엔드가 메뉴·옵션·가격을 기준 데이터와 대조해 검증합니다.
2. 주문 저장과 주문번호 발급을 **하나의 트랜잭션**으로 묶습니다. 주문이 일부만 저장되지 않도록 처리하고 저장 성공 후에만 번호를 반환합니다.
3. 번호는 **DB 자동 증가 방식**으로 발급합니다. MVP에서는 초기화하지 않고 중간 번호 누락을 허용합니다. 주문 저장이 실패해도 번호가 소비될 수 있으며 이를 반드시 재사용할 필요는 없습니다.
4. 주문 시도마다 고유한 요청 ID를 사용합니다. 응답 유실 등의 이유로 같은 주문을 재전송할 때는 같은 ID를 유지합니다.
5. 같은 요청이 반복되면 기존 주문 결과를 반환하며 새 주문을 만들지 않습니다. 동시에 들어온 요청도 중복 저장되지 않도록 DB 차원의 중복 방지를 설계합니다.

구체적인 JSON 필드와 테이블, 동일 ID에 다른 주문 내용이 전달된 경우의 처리 등은 API·DB 설계 문서에서 정합니다. 프론트에서 버튼을 잠그는 것만으로 중복 주문 방지를 끝내지 않습니다.

## 7. 음성 안내와 실패 처리 — 구현 예정

음성 안내는 사용자가 다음에 할 일을 알려주는 출력입니다. Whisper의 음성 인식과는 별개이며, 녹음 안내를 재생할지 TTS로 읽을지는 미정입니다. TTS는 텍스트를 음성으로 바꾸는 기능입니다.

프론트는 안내 재생·중단과 녹음 상태를 관리합니다. 메뉴 선택 단계에서는 메뉴 선택 안내를, 옵션 단계에서는 해당 옵션 안내를 제공합니다.

| 상황 | 사용자에게 보여줄 처리 방향 |
| --- | --- |
| 마이크 권한 거부 | 권한 허용 방법과 터치 주문 경로 안내 |
| 빈 녹음 또는 처리할 수 없는 파일 | 다시 녹음하도록 안내 |
| 인식 결과가 불명확함 | 다시 말하도록 요청하고 현재 단계 유지 |
| 메뉴나 옵션으로 해석할 수 없음 | 선택 가능한 항목을 안내하고 재입력 요청 |
| 추천 후보가 없음 | 조건을 바꾸거나 메뉴판에서 선택하도록 안내 |
| 음성 처리 지연·실패 | 처리 상태 또는 실패를 표시하고 재시도·터치 경로 제공 |
| 주문 저장 실패 또는 결과 불명확 | 성공으로 표시하지 않고 상태 확인·복구 경로 제공 |

Whisper의 `transform()` 점수로 성공 여부를 판단한다는 아이디어는 검증 전입니다. 사용할 라이브러리의 실제 출력과 평가 결과를 확인해 기준을 정합니다. 인식 점수 하나를 주문 내용의 정확성 보장으로 사용하지 않습니다.

프론트에는 최소한 ‘녹음 중’, ‘처리 중’, ‘선택 대기’, ‘실패’ 상태를 구분해 표시하는 방향입니다. 구체적인 시간 제한과 안내 문구는 후속 설계에서 정합니다.

## 8. 학습과 서비스 실행은 분리해서 생각합니다

**서비스 실행**은 사용자의 음성을 지금 텍스트로 바꾸는 작업입니다. **추가 학습**은 음성과 정답 문장 등을 이용해 모델을 개선하는 별도의 작업입니다.

```text
추가 학습 경로 — 검토 중
음성 + 정답 문장 준비
  → 학습 실행
  → 학습에 사용하지 않은 평가 데이터로 확인
  → 사용할 모델 버전 선택
  → 서비스 실행 환경에서 해당 모델 불러오기

실제 주문 경로 — 구현 예정
사용자 녹음 → 선택된 모델로 음성 인식 → 텍스트 반환
```

주문이 들어올 때마다 모델을 학습시키는 구조는 아닙니다. 사용자의 음성을 자동으로 학습 데이터에 추가하는 기능도 확정하지 않았습니다.

GPU 종류·메모리·실행 OS를 확인한 뒤 PyTorch 등 실행·학습 도구와 컨테이너 환경을 정합니다. 모델을 FastAPI와 같은 환경에 둘지 별도 실행 환경으로 나눌지도 그때 결정합니다.

## 9. 개발 환경과 외부 배포의 차이

### 현재: 팀원 컴퓨터에서 개발

- Docker Compose로 프론트·백엔드·DB를 실행합니다.
- PC의 소스 파일을 컨테이너와 연결하여 수정 내용을 자동 반영합니다.
- DB 데이터는 `postgres_data` 볼륨에 보관하여 일반적인 컨테이너 종료·정리 후에도 유지합니다.
- DB가 준비된 뒤 백엔드가, 백엔드가 준비된 뒤 프론트가 시작하도록 설정되어 있습니다.
- 앱 포트는 `127.0.0.1`에 연결되어 해당 컴퓨터에서만 접속할 수 있습니다.
- DB 포트는 호스트에 공개하지 않습니다.
- 팀원별 DB는 별개입니다. 같은 Compose 설정을 사용해도 데이터까지 자동 공유되지는 않습니다.

실행 명령과 문제 해결 방법은 [README](../README.md)를 참고하세요.

### 예정: 실제 키오스크가 접속하는 서비스

| 대상 | 방향 |
| --- | --- |
| 프론트 | Vite로 빌드한 화면을 Vercel에 배포 |
| 백엔드·Whisper | GPU와 실행 조건을 확인한 뒤 장소·구성 결정 |
| PostgreSQL | 배포할 DB의 위치와 연결 설정 결정 필요 |

Vercel에 화면을 올리는 것만으로 Whisper 서버와 DB까지 배포되지는 않습니다. 현재 Vite 개발 프록시도 빌드된 화면 파일에 포함되지 않으므로, 배포 환경에 맞는 API 주소와 요청 전달 설정이 필요합니다.

공개 환경에서는 HTTPS와 마이크 사용 조건을 실제 키오스크 브라우저에서 확인해야 합니다. 화면과 API 주소가 다르면 브라우저의 교차 출처 요청 허용 설정인 CORS도 검토해야 합니다.

현재 Compose는 개발용입니다. 외부 배포 때는 개발용 자동 재실행 설정, DB 접속 정보, 파일 보관 및 로그 관리 등을 배포 환경에 맞게 별도로 설정합니다.

## 10. 데이터와 진단에 대한 기본 방향

다음은 후속 구현에서 지킬 설계 방향이며 아직 구현 완료된 기능은 아닙니다.

- DB 접속 정보나 외부 서비스 비밀키는 프론트에 넣지 않고 서버 설정으로 관리합니다.
- 음성 파일의 크기·길이·형식을 확인하고 처리 실패를 사용자에게 알립니다. 구체적인 제한값은 미정입니다.
- 음성 원본을 계속 보관하는 것을 기본 전제로 삼지 않습니다. 학습에 활용하려면 수집·사용 범위와 보관·삭제 기준을 먼저 정합니다.
- 모델 파일, 녹음 원본, 비밀 설정은 Git에 올리지 않습니다.
- 문제를 찾을 수 있도록 요청 식별 정보, 처리 시간, 실패 단계를 기록하는 방향입니다. 음성 내용이나 비밀키를 무조건 로그에 남기지 않습니다.
- 다음 고객이 시작할 때 이전 고객의 선택과 인식 결과가 섞이지 않도록 주문 상태를 초기화해야 합니다. 초기화 시점과 비활동 시간 처리는 미정입니다.

구현은 **메뉴 조회와 터치 주문 → 음성 인식 연결 → 메뉴 해석과 추천 → 실패·재시도 처리** 순으로 진행하는 것을 제안합니다. 주문 저장은 위에서 확정한 규칙에 따라 API·DB 세부 설계를 먼저 작성합니다. 주요 결정이 바뀌면 프로젝트 개요와 이 문서도 함께 갱신합니다.
