# 프로젝트 개요 — 음성 주문 보조 시스템

> 이 문서는 프로젝트의 목적, 사용자 경험, MVP 범위를 정의하는 기준 문서입니다.
> 이후 기획·디자인·개발을 수행하는 팀원과 AI는 이 문서를 먼저 읽습니다.
> ‘확정’, ‘검토 중’, ‘미정’을 구분하며, 미정 사항을 임의로 구현 요구사항으로 확정하지 않습니다.

## 1. 프로젝트 이름

**음성 주문 보조 시스템**

## 2. 한 줄 설명

**주요 대상자인 고령층이 터치 또는 음성으로 음료를 선택하고, 취향에 맞는 메뉴를 추천받아 옵션 선택과 주문번호 발급까지 진행하는 카페 키오스크 서비스입니다.**

## 3. 핵심 문제

아래 문제를 해결하고자 합니다. 

- 복잡한 메뉴판과 여러 단계의 화면 전환 때문에 원하는 음료를 주문하기 어렵습니다.
- 메뉴 이름을 모르거나 무엇을 마실지 정하지 못하면 메뉴 선택 자체가 어렵습니다.
- 터치 조작이나 화면의 글을 읽는 것만으로 주문을 진행하기 어려운 사용자가 있습니다.
- 음성 인식이 잘못되거나 원하는 메뉴가 추천되지 않았을 때 다시 시도할 수 있는 명확한 안내가 필요합니다.

서비스는 **간소화된 화면, 음성·텍스트 안내, 터치·음성 선택, 취향 기반 추천**으로 이 과정을 돕습니다.

## 4. 타깃 사용자

### 주요 사용자

- **고령층**을 주요 대상으로 합니다. 특히 기존 키오스크의 화면과 조작 방식에 어려움을 느끼는 카페 이용자의 주문을 돕습니다.

### 함께 고려하는 사용자

- 메뉴 이름을 정확히 모르지만 원하는 맛이나 음료 종류는 말할 수 있는 이용자.
- 취향을 설명하고 메뉴를 추천받고 싶은 이용자.
- 상황에 따라 터치와 음성을 선택해서 사용하고 싶은 이용자.

## 5. 서비스의 핵심 원칙

1. **터치와 음성은 같은 주문 과정으로 연결합니다.** 두 방식의 최종 주문 데이터 형식은 동일합니다.
2. **메뉴를 아는 사용자와 추천이 필요한 사용자를 구분합니다.** 특정 메뉴를 말하면 메뉴 선택으로, 취향을 말하면 추천으로 연결합니다.
3. **실제 메뉴판에 등록된 메뉴를 기준으로 동작합니다.** 메뉴명 확인과 추천 후보는 팀이 준비한 메뉴 데이터를 사용합니다.
4. **음성 안내 중에도 사용자 입력을 받을 수 있어야 합니다.** 마이크 버튼을 누르면 재생 중인 안내를 중단하고 음성 입력을 시작합니다.
5. **실패와 재시도 경로를 제공합니다.** 인식이 어렵거나 선택으로 해석할 수 없으면 다시 입력하도록 안내합니다.
6. **주문 화면에서 메뉴판에 접근할 수 있어야 합니다.** 간소화된 메뉴판과 전체 메뉴판 보기 기능을 제공합니다.

## 6. 사용자 흐름

### 6.1 시작 화면

- 화면 가운데에 로고를 배치합니다.
- 로고 아래에는 **‘주문하기’ 버튼 하나**를 배치합니다.
- 주문하기 버튼을 누르면 주문 화면으로 이동합니다.

### 6.2 기본 주문 화면

| 위치 | 구성 |
| --- | --- |
| 맨 위 | ‘마이크 버튼을 눌러 음성 주문 및 추천을 받을 수 있습니다’라는 취지의 텍스트·음성 안내 |
| 중간 | 간소화된 메뉴판과 ‘메뉴판 보기’ 버튼 |
| 맨 아래 | 음성 입력을 시작하는 마이크 버튼 |

- 메뉴판 보기 버튼으로 전체 메뉴판을 확인하거나 확대할 수 있도록 합니다.
- 마이크 버튼을 누르면 재생 중인 음성 안내를 중단하고 음성 입력을 시작합니다.
- 사용자가 **녹음 종료 버튼**을 누르면 녹음을 마치고 음성 인식을 요청합니다. 무음 감지나 제한 시간을 기본 종료 방식으로 사용하지 않습니다.
- 버튼을 누르지 않고도 사용자 발화를 감지해 안내를 중단하는 기능은 현재 확정 범위가 아닙니다.

### 6.3 터치로 주문하는 경로

1. 메뉴판에서 메뉴를 선택합니다.
2. 옵션 선택으로 이동합니다.
3. 선택된 메뉴와 옵션으로 주문 데이터를 만듭니다.
4. 최종 주문 내용을 보여주고 사용자가 ‘주문 확정’ 버튼을 누릅니다.
5. 백엔드가 주문을 검증하여 PostgreSQL에 저장하고, 저장에 성공하면 주문번호를 표시합니다.

터치 경로는 기존 키오스크와 유사한 주문 흐름을 제공합니다. 음성 입력을 요구하지 않습니다.

### 6.4 음성으로 주문하거나 추천받는 경로

마이크 버튼 입력 → 녹음 → **녹음 종료 버튼 입력** → 음성 인식 → 인식 결과 확인 → 아래 경로로 분기합니다.

| 경우 | 처리 |
| --- | --- |
| 음성 인식이 제대로 되지 않음 | 다시 말하도록 음성·텍스트로 안내 |
| 등록된 메뉴명에 해당하는 주문 | 해당 메뉴를 선택하고 옵션 단계로 이동 |
| 구체적인 메뉴명 없이 취향이나 조건을 설명함 | 조건에 맞는 메뉴 추천 |
| 메뉴 선택이나 추천 요청으로 해석하기 어려움 | 입력을 다시 요청 |

예시: **‘차갑고 달달한 티 종류 아무거나’ → 취향·조건 기반 추천**.

원안의 ‘메뉴명 일치 → 바로 주문’은 현재 **추천 단계를 건너뛰고 메뉴를 선택하는 흐름**으로 정리합니다. 옵션 선택을 생략하거나 즉시 주문을 확정한다는 뜻으로 구현하지 않습니다.

인식된 텍스트에서 발췌한 메뉴 워딩이 **등록 메뉴 집합에 있으면 일치, 없으면 불일치**로 판단합니다. 유사 표현을 임의로 등록 메뉴명과 같은 것으로 처리하지 않습니다. 메뉴명이 불일치하더라도 추상적인 취향·조건 표현이 있으면 추천 경로로 연결합니다. 인식 실패나 의미 없는 입력은 재입력을 요청하며, 텍스트에서 메뉴 워딩과 취향·조건을 발췌하는 구체적인 방법은 별도 설계합니다.

### 6.5 추천 결과에서 선택하기

- LLM이 추천 후보 1개를 직접 선택하거나, 확인 질문·자료 부족을 안내합니다.
- 메뉴 사진을 누르거나 음성으로 메뉴를 선택할 수 있습니다. 
- 사진 선택 또는 음성 입력으로 메뉴를 고를 수 있음을 음성·텍스트로 안내합니다.
- 메뉴 선택으로 해석하기 어려운 음성이 들어오면 다시 입력하도록 안내합니다.
- **‘재추천’ 버튼**을 제공합니다.
- 재추천을 누르면 초기 음성 입력 단계로 돌아가 조건을 다시 받습니다.
- 메뉴 선택이 완료되면 옵션 단계로 이동합니다.

### 6.6 옵션 선택

메뉴 선택 후 옵션을 고를 수 있음을 음성·텍스트로 안내하고, 다음 두 단계를 순서대로 진행합니다.

1. **HOT / COLD 선택**
2. **매장 / 포장 선택**

터치와 음성으로 선택한 결과는 같은 형식으로 정리합니다. **메뉴별 제공 불가 옵션 처리, 옵션 변경, 이전 단계 이동은 현재 구현 범위에서 제외하며 추후 구현합니다.**

### 6.7 주문 기록 및 주문번호

- 주문번호 발급을 위해 **선택한 메뉴와 속성(선택 옵션 포함)을 담은 공통 주문 JSON**을 만듭니다. 터치와 음성의 결과는 동일한 구조로 백엔드에 전달합니다. JSON은 데이터 전달 형식이며, 별도의 JSON 파일 저장을 뜻하지 않습니다.
- 최종 주문 내용을 화면에 표시하고 사용자가 **‘주문 확정’ 버튼**을 누른 후 저장을 요청합니다.
- 백엔드는 메뉴·옵션·가격을 기준 데이터와 대조해 검증합니다.
- **PostgreSQL을 주문 기록의 유일한 원본**으로 사용합니다. CSV 저장·내보내기는 MVP에 포함하지 않으며, 추후 필요할 때 DB에서 내보내는 기능으로 추가합니다.
- 주문 저장과 주문번호 발급은 하나의 트랜잭션으로 처리합니다. 즉, 주문이 일부만 저장되지 않도록 하나의 작업으로 묶고 저장 성공 후에만 번호를 응답합니다.
- 주문번호는 **DB 자동 증가 방식**으로 발급합니다. MVP에서는 초기화하지 않으며 중간 번호가 빠지는 것을 허용합니다. 실패한 저장 시도에 사용된 번호를 반드시 재사용하지는 않습니다.
- **동일 요청의 중복 처리와 요청 ID 기반 동시 요청·응답 유실 대응은 추후 구현합니다.** 현재 MVP에서는 동일 요청의 재전송이 기존 주문 결과를 반환한다고 보장하지 않습니다.
- JSON에 선택한 메뉴와 속성을 담는 목적은 확정되었습니다. 구체적인 필드명·자료형과 PostgreSQL 테이블 관계는 API·DB 설계 문서에서 별도 정의합니다. 주문 저장·번호 발급 규칙은 설계이며 아직 구현 완료된 기능은 아닙니다.

## 7. 음성 인식과 추천 구상

### 7.1 음성 인식

- 사용 예정 모델: `openai/whisper-large-v3-turbo`
- 두 모델 중 최종 서비스 모델을 선택할지, 비교 평가에 모두 사용할지는 미정입니다. 항상 둘을 함께 실행하는 구조로 가정하지 않습니다.
- 팀이 제시한 입력 데이터 형식은 **MP3**입니다.
- 모델을 직접 실행하고 추가 학습하는 방향을 고려하고 있습니다. 학습 실행 여부, 데이터 구성, 방식, GPU 환경은 아직 확정되지 않았습니다.
- 브라우저 녹음 형식과 MP3 변환 여부, 서버에서의 음성 전처리는 별도 설계합니다.
- Whisper는 **음성을 텍스트로 변환**하는 역할입니다. 메뉴 추천과 주문 옵션 해석은 별도의 로직이 필요합니다.

#### 음성 인식 실패 판정

Whisper가 발화를 제대로 알아들을 수 없다고 평가하는 정도를 기준으로 인식 실패를 판단하고, 실패하면 재입력을 안내합니다. 다만 실제 사용하는 라이브러리의 출력 지표와 임계값은 아직 정하지 않았습니다. 특정 메소드나 점수가 발화의 정답 여부를 보장한다고 가정하지 않으며, 실제 주문 음성으로 기준을 검증해야 합니다.

### 7.2 LLM 직접 메뉴 추천

현재 메뉴는 공통 카탈로그 45종이다. 메뉴명과 일치하면 바로 선택하고, 취향·조건 발화는 전사 원문과 현재 DB 메뉴 정보를 LLM에 전달한다. LLM이 후보 1개 또는 확인 질문·자료 부족을 결정하며 서버는 메뉴 ID·가격·판매·온도·근거를 검증한다.

이전의 11종 자료, 맛 점수 행렬, 반복 평가·평균 생성기와 CSV 정렬 추천은 제거했다. 긍정·부정 취향은 원문 맥락으로 LLM이 판단하며 높은/낮은 점수 4개를 고르는 규칙은 사용하지 않는다.

45종 설명·우유·카페인·알레르기 자료는 현재 미확인으로 표시돼 있다. 근거가 부족한 맛·성분 요청은 질문 또는 자료 부족 안내로 처리한다. 자세한 실행 방법과 제한은 [LLM 직접 추천](llm-direct.md)을 따른다.

## 8. MVP 범위

### 포함하는 기능

- 로고와 주문하기 버튼이 있는 시작 화면.
- 음성·텍스트 안내가 있는 기본 주문 화면.
- 간소화된 메뉴판과 전체 메뉴판 보기·확대 기능.
- 터치 메뉴 선택과 옵션 선택.
- 마이크 버튼으로 시작하고 녹음 종료 버튼으로 끝내는 음성 입력 및 안내 재생 중단.
- Whisper를 이용한 음성 인식 연결.
- 인식 실패 또는 해석 불가 시 재입력 안내.
- 등록 메뉴명에 대응하는 메뉴 선택.
- 추상적인 취향·조건에 따른 메뉴 추천.
- LLM 직접 추천 후보 1개 및 확인 질문·자료 부족 안내.
- 추천 사진 터치·음성 선택 및 재추천 경로.
- HOT/COLD, 매장/포장 옵션 선택.
- 터치·음성 공통 주문 JSON 생성.
- 최종 주문 확인 후 PostgreSQL에 주문 저장 및 자동 증가 주문번호 표시.

### 현재 확정 범위에 포함하지 않는 기능

다음은 영구 제외가 아니라 **별도 합의 없이 MVP에 추가하지 않을 항목**입니다.

- 메뉴별 제공 불가 옵션 처리, 옵션 변경, 이전 단계 이동: 추후 구현 예정.
- 동일 요청의 중복 주문 방지와 요청 ID 기반 동시 요청·응답 유실 대응: 추후 구현 예정.
- 실제 결제, 카드 단말기, POS 연동.
- CSV 주문 저장·내보내기.
- 주문번호의 실물 출력과 프린터 연결.
- 회원가입, 로그인, 개인별 주문 이력 기반 추천.
- 별도 관리자 콘솔과 다매장 운영.
- 마이크를 누르지 않는 상시 청취 및 자유로운 실시간 대화.
- 장바구니·다품목·수량 변경의 상세 흐름: 현재 구체적인 워크플로가 정해지지 않았습니다.
- 추가 학습의 실제 수행: 검토 중이며 MVP의 필수 완료 조건으로 아직 확정하지 않았습니다.
- 여러 메뉴와 수량 선택은 MVP에 포함하지 않았습니다. 

### MVP 완료 확인 기준

- 터치로 메뉴와 옵션을 선택하고 주문번호까지 받을 수 있습니다.
- 음성으로 등록된 메뉴를 선택하고 동일한 옵션·주문 흐름으로 진행할 수 있습니다.
- 취향을 말하면 메뉴 후보가 표시되고, 터치 또는 음성으로 선택할 수 있습니다.
- 인식 실패와 재추천 시 다시 시도할 경로가 동작합니다.
- 마이크 버튼을 누르면 재생 중인 안내가 멈춥니다.
- 터치·음성의 결과가 같은 주문 데이터 형식으로 기록됩니다.

인식 정확도, 추천 만족도, 응답 시간의 수치 목표는 아직 정하지 않았습니다. 임의의 성능 목표를 확정 요구사항으로 추가하지 않습니다.

## 9. 기술 스택과 현재 구현 상태

| 영역 | 선택 | 상태 |
| --- | --- | --- |
| 프론트 | React + Vite + TypeScript | 개발 환경 구성 완료 |
| 백엔드 | Python + FastAPI | 개발 환경 구성 완료 |
| DB | PostgreSQL | 연결 확인 완료, 도메인 테이블은 설계 필요 |
| 로컬 실행 | Docker Compose | 프론트·백엔드·DB 함께 실행 가능 |
| 프론트 배포 | Vercel | 선택 완료, 외부 배포는 별도 진행 |
| 음성 인식 | Whisper large-v3 / large-v3-turbo | 모델 연결·선택·평가 필요 |
| 모델·백엔드 실행 환경 | GPU 확인 후 결정 | 미정 |
| 음성 안내 방식 | 녹음 음성 또는 TTS 등 | 미정 |

FastAPI는 모델 학습 도구가 아니라 화면의 요청을 받고 모델 및 주문 처리 로직과 연결하는 API 서버입니다. 학습 도구와 GPU 환경은 별도로 구성합니다.

현재 저장소에는 연결 확인용 화면과 API가 있으며, 서비스 기능이 완성된 상태는 아닙니다. 개발 환경 실행 방법은 [README](../README.md)를 참고합니다.

## 10. 주요 질문에 대한 결정 사항과 남은 설계

후속 답변을 반영한 결정 사항입니다. ‘추후 구현’ 항목은 현재 MVP의 필수 구현·완료 기준에 포함하지 않습니다.

| 번호 | 질문 | 결정 사항 | 남은 설계 또는 후속 작업 |
| --- | --- | --- | --- |
| 1 | 서비스 이름과 타깃 사용자 | **음성 주문 보조 시스템**, 주요 대상자는 **고령층** | 세부 사용자 시나리오는 필요에 따라 구체화 |
| 2 | 음성 입력 종료 방식 | **녹음 종료 버튼**으로 입력 종료 | 녹음 형식·변환 및 전처리 설계 |
| 3 | 인식 실패와 메뉴명 일치 기준 | Whisper가 제대로 알아듣지 못했다고 평가하는 정도로 실패 판단. 발췌한 메뉴 워딩이 등록 메뉴 집합에 있으면 일치, 없으면 불일치. 메뉴명 불일치 시 추상적인 취향·조건 표현이 있으면 추천으로 연결 | 모델 출력 지표·임계값, 워딩·취향 발췌 방법 검증 |
| 4 | 추천 방식 | 전사 원문과 현재 45종 메뉴를 읽은 LLM 직접 선택 | 미확인 메뉴 설명·성분 자료 보완 |
| 5 | 추천 개수 | 최신 직접 추천은 후보 1개 또는 질문·자료 부족. 이전 Max/MIN 4 점수 방식 제거 | 다중 대화 지원 검토 |
| 6 | 제공 불가 옵션·옵션 변경·이전 단계 이동 | **현재 구현하지 않으며 추후 구현 예정** | 후속 단계에서 메뉴별 제약과 이동·변경 흐름 설계 |
| 7 | 공통 주문 JSON과 DB 관계 | 주문번호 발급을 위해 **선택한 메뉴와 속성**을 담은 JSON 필요 | 구체적인 필드명·자료형과 PostgreSQL 테이블 관계 정의 |
| 8 | 동일 요청 ID의 동시 요청·응답 유실 처리 | **동일 요청 처리는 추후 구현 예정** | 후속 단계에서 API·DB 중복 방지와 재시도·동시성 설계 |

## 11. 이후 작업하는 AI와 팀원을 위한 지침

- 핵심은 **사용자가 카페 메뉴를 고르고 옵션을 선택해 주문번호를 받는 경험**입니다.
- 위의 사용자 흐름을 먼저 구현하고, 이를 위해 필요한 기술만 추가합니다.
- 메뉴 데이터, 모델 입력·출력, 주문 데이터 사이의 책임을 구분합니다.
- 검토 중인 아이디어를 검증된 API나 확정된 알고리즘으로 표현하지 않습니다.
- 새로운 요구사항이 합의되면 이 문서를 업데이트하여 코드·설계와의 차이를 줄입니다.
